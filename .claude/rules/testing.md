# Verification: the long form

The short form — the commands themselves and which half to run — is in `AGENTS.md`. This is the reasoning behind each rule, kept out of the always-loaded file. The developer-facing version is `docs/development/testing.md`.

## How much to run

There is no single entry point. Run the checks directly, and run only the half the change touches — Python and `web/` are independent. How much of that half to run is a judgement about the host and about who is waiting: the static checks are seconds and are run whole, while the suite is minutes and is the part to narrow to what covers the change when the run has to fit a bounded budget.

**Use `scripts/qt` while iterating and `scripts/qtest uv run pytest` once before the commit.** Do not hand-pick a subset instead — see below for why that does not work here. Both are cheap on a machine of this size, which is what makes the full run the right close: the suite is about two minutes here, not the 70-odd minutes it costs on a small deployment host. That gap is the whole reason the `developer` skill's own default is narrower than this file's, and why it now yields to `USER.md` rather than ordering either one.

## Lint scope

`scripts/` is in it because it was in no documented command at all and a whole-repo `ruff check .` was therefore red on three pre-existing files there, handing back noise unrelated to whatever it was checking. Naming the directory does **not** reopen the `extend-include` question below: `scripts/qtest` has no `.py` suffix, so ruff still walks past it, and pulling it in is a separate decision with its own argument.

`docker/devbox/` is in that first command because three of the Python programs the devbox image ships carry no `.py` suffix — they are on the container's `PATH` and invoked by name — so ruff, which discovers by extension, walked past the exec server, the credential helper and the policy seeder and reported the directory clean. `[tool.ruff] extend-include` names those three one by one; a `scripts/*` glob would hand ruff the supervisor beside them, which is `/bin/sh`. That list is hand-maintained, so `tests/test_lint_scope.py` walks the directory for a Python shebang without a `.py` suffix and requires each hit to be named — otherwise a fourth program added later is unlinted and the command still says everything passed. `scripts/qtest` is the same shape and is deliberately outside this scope.

`docker/istota/` and `docker/browser/` are in it for the plainer reason: both hold ordinary `.py` files that ship in an image and live outside `src/`, and no documented command reached either. `tests/test_lint_scope.py` now walks `docker/` for `.py` files and requires each one's directory to be named in the command above, so the next one added elsewhere under `docker/` fails a test rather than going unlinted while the command reports everything passing. `docker/browser/` is what that guard found on the day it was written — five files, clean as it happens, and unlinted by every documented command since they were added.

## What to install

**What to install: `uv sync --extra test`.** A bare `uv sync` is never right — everything the suite needs from `[project.optional-dependencies]` is left out, and the result is hundreds of `ModuleNotFoundError` collection errors that read as a code regression. `--all-extras` works and costs about 1.1 GB in the venv; the `test` extra is `all` minus the two heavy ML ones and costs 291 MB, which matters because the venv is per-worktree and per-container. It is what `scripts/setup.sh` and `docker/test/Dockerfile` install. The difference is `memory-search` (torch, sentence-transformers) and `whisper` (faster-whisper, av, onnxruntime); every heavy import in `src/` is inside a function, deliberately, so nothing needs them to collect, and the one test that needs them at run time carries the `ml` marker. Use `--all-extras` when you want that test or the real libraries to hand-test against. Test-only dependencies belong in the `dev` group, never in an extra — `jinja2`, `psutil` and `pyyaml` each used to arrive as somebody else's transitive, and `tests/test_lean_install.py` is what keeps that from happening again. It sweeps every package the test suite imports and requires each to be reachable from `uv sync --extra test` itself, rather than naming them one at a time: the hand-written pair was why the same bug landed three times. Reachable, not merely declared — a test-only package in the `docs` extra is declared and is still missing from every lean install.

## The deselected markers

**Nine markers are deselected by default, and none of them runs unless you ask.** Each has a different prerequisite, so they are selectable independently: `integration` (a live Nextcloud, Garmin credentials, or a running devbox whose exec server answers a `ping` — still a host shell for the devbox half, since the skill CLI resolves its socket from the config file and the config directory is bound into no sandbox, but it now skips honestly there instead of mistaking a proxy refusal for an answer), `live` (a Claude Code credential or an API key; costs money, and skips rather than fails without one — `ISTOTA_LIVE_TIER=1` turns that skip into a failure), `linux` (a real kernel and a usable bubblewrap), `image` and `smoke` (a Docker daemon), `full` (a Docker daemon, minutes, and the network — `provision-nc.sh` fetches Talk and Calendar from the Nextcloud app store at first install), `testbed` (a Docker daemon and no istota image — the wire-level email suite, which runs a real IMAP/SMTP server and calls `poll_emails` against it with no stack at all), `deploy` (a Docker daemon, the network, and about three minutes — the Ansible role converged on a systemd container), `ml` (one of the two heavy ML extras). A tenth, `requires_dac`, is not deselected — it skips itself where the process can bypass permission bits, which is what happens as root inside the Linux runner. ## The discretionary tiers

`image`, `smoke`, `full`, `testbed` and `deploy` require `-n0`: their fixtures are session-scoped and build one tagged image, and N xdist workers would each race to build it — the two compose tiers would also bring up their own stacks under one project prefix and sweep each other's projects. `smoke` and `full` are the same fixtures over two compose files: the lean stack (one container, entrypoint bypassed, config rendered on the host) and the deployment as shipped, which is the only thing that executes `provision-nc.sh` or reaches the half of `entrypoint.sh` past the config write. Before a release, add `-m full -n0`, `-m image -n0 --platform amd64` (checks the deployment architecture; since ISSUE-280 the devbox image builds natively too, so a plain `-m image` already runs its assertions) and `scripts/test-upgrade.sh --from-floor --shape volume`. Three of the tiers carry a negative control that must go **red** — `scripts/test-image-negative-control.sh`, `scripts/test-deploy-negative-control.sh`, and the same broken image handed to the upgrade tier through `ISTOTA_IMAGE_TAG`. `test-image-negative-control.sh` covers both images: one control for the istota half, and ten for the devbox half, because no single broken image reaches all twenty-seven of that file's assertions — and several of the ten turn a neighbour's assertion red for the wrong reason, which is what the extra ones separate. Six assertions there have no control on purpose, each failing closed: four positive existence checks against a named absolute path, an exact `Cmd`, or a resolved path compared to a directory it must not be under, the graceful-stop assertion, and the unconfigured hold. Each control names the exact node ids it must turn red and requires them in pytest's `FAILED` summary, since a control can otherwise pass on an unrelated failure. On a tier asserting against an artifact, reading the test tells you almost nothing about whether it can fail. Details and a when-to-run-each table in `docs/development/testing.md`.

**The `deploy` tier is the bare-metal half, and it closed the largest hole in this list** (ISSUE-439). `AGENTS.md` calls bare metal via Ansible the only canonical deployment shape, because it is the only one where the sandbox actually works — and nothing in the repository had ever run `ansible-playbook`. The fourteen `tests/test_ansible_*.py` files parse the role's YAML and assert on the parse, which cannot see a unit systemd refuses, a rendered config the loader rejects, or a task ordering that only breaks when the tasks run. `scripts/test-deploy.sh` boots `docker/test/Dockerfile.deploy` — Debian 13, systemd as PID 1, and deliberately almost nothing else, so the tier exercises `install.sh`'s own apt steps rather than a baked layer — and drives the real `deploy/install.sh --headless` inside it. `istota doctor` is the oracle, as it is for `image` and `smoke`.

**It is not `docker/test/Dockerfile`, and the difference is PID 1.** That image runs with `--init`, chosen so orphaned grandchildren get reaped, with a comment saying "on a real host systemd does this job" — which makes it the one container the role cannot converge on, since every `systemctl enable` and `start` needs systemd as PID 1 with a writable cgroup tree. PID 1 is the whole of it now: ISSUE-440 moved that image to `python:3.12-slim-trixie`, so both are Debian 13 and the bases no longer differ — which used to be the second reason for the split and is no longer one. The run flags carry over and gain two: `--cgroupns=host` with a writable `/sys/fs/cgroup` for systemd, and `systempaths=unconfined` beside `seccomp=unconfined` — the pair `.claude/rules/testbed.md` documents, without which bwrap creates a user namespace and then cannot mount a procfs inside it.

**Three controls, and two of them found something on their first run.** `scripts/test-deploy-negative-control.sh` breaks a unit file, a rendered config key, and the sandbox grant. The sandbox control caught the tier's own `bwrap` probes running as *root* — who `docker exec` is by default — while doctor probed as the daemon's unprivileged user: the probes passed on a container deliberately run without the grant, two answers to one question with the reassuring one about a user that never runs a task. The probes now run as `istota` and a fourth assertion requires the two readings to agree. The config control established that a bad render fails the *play* rather than reaching the assertions about it, because the role runs `istota` CLI commands against the rendered config partway through — so that control asserts the converge failed and no test passed, rather than naming node ids, and the two assertions in `TestTheRenderedConfigLoads` are uncontrolled and fail closed.

**What it does not cover, stated so the tier is not read as covering the deploy end to end**: reboot ordering and the `Require`/`After` relationship between the app units and the rclone mount unit; a real FUSE mount against a real remote; and anything about the host's own kernel, which a container shares rather than owns. It also converges with rclone, zram, Talk and the web UI off — `tests/deploy/conftest.py` gives each concession its reason. Idempotence re-applies the *playbook* rather than the whole installer, because the bootstrap's `ansible-galaxy collection install --force-with-deps` re-downloads three collections on every run and made a truncated fetch read as a role defect.

**What a scenario declares, and the four rules for adding one.** `smoke` and `full` are one fixture over eight profiles — a profile is a shape plus the services it runs, declared as `@pytest.mark.profile("forge")` and booted once per session, so a test must not assume an empty table. Anything added to `testbed/` is bound by four rules, the first three enforced in the default suite: a service points the daemon at itself only through a variable `docker/istota/render-config.sh` reads **and** `docker/docker-compose.yml` passes through (add one to both as a reviewed product change; never side-load from the fixture), a stub bound off loopback must be given a credential to expect, a negative assertion takes a watermark *and* a discriminating column, and a service whose client negotiates capabilities is run for real rather than stubbed. The prompt goldens (`tests/test_prompt_golden.py`) are in the default suite and need no container; regenerate with `uv run env ISTOTA_UPDATE_GOLDEN=1 pytest tests/test_prompt_golden.py -n0` and review the diff. Reference: `.claude/rules/testbed.md`.

**All seven tiers need Docker — the Linux tier unless it runs natively — so a sandboxed task cannot run any of them; check `ISTOTA_SANDBOXED` before you plan around one.** A task has no Docker access at all now: no socket is bound into a sandbox at any path and no `DOCKER_HOST` is exported, so the `docker` binary a task can still resolve under the read-only `/usr` bind fails at connect; the Linux tier's container mode also wants `CAP_SYS_ADMIN` and `CAP_NET_ADMIN`, which is what the sandbox exists to deny. **The Linux tier's native mode is not a way round that**: a task's own sandbox passes `--unshare-user --disable-userns` wherever bwrap supports it, which switches off the nested user namespace a second bwrap needs, so on a Linux deployment host both routes are shut and no value of `ISTOTA_LINUX_TIER_MODE` opens either. Both shell drivers refuse up front and say so, and `test-linux.sh` probes for that nested namespace rather than asserting it, so a deployment on bwrap older than 0.8 is told the truth about which boundary stopped it. **When a change touches the sandbox, the network proxy, the skill proxy, a migration or the image, say so in the merge request, name the tier that covers it, and ask for the run before merge.** Report the default suite as what it is: it patches `_bwrap_available` and checks argv, so it has never executed the sandbox path you changed. The tier that does is `smoke`, and it carries three witnesses that distinguish a sandbox that ran from one that was skipped: `tests/smoke/test_sandbox_in_stack.py` reads the database masks from inside a live task in the shipped image, the same file requires the task's control directory to refuse both an append to `system_prompt.txt` and a file planted anywhere in it, while a sibling in the per-user temp directory — a *different* directory, which is the point — stays writable, and `tests/smoke/test_sandbox_repos_isolation.py` requires another admin's repos subtree to be missing from the same namespace.

## Choosing what to run

**Do not choose the affected tests by reading the code — use `scripts/qt`.** The intuitive methods were measured against what actually executes, and both are wrong in both directions. Editing `shell_argv()` in `shell_exec.py` touches 101 tests across six files; the name-matched `tests/test_shell_exec.py` holds 12 of them, and grepping `tests/` for `shell_exec` also finds 12 — it adds three files that never exercise the function and misses `test_scheduler.py` (35 tests), `test_heartbeat.py` (26) and `native/test_tools_bash.py` (25), which are exactly the three consumers this file documents as depending on its `pipefail` semantics. Dependence runs through call chains, not through text, so those files never mention the module they depend on. The same grep over-selects six-fold on `git_remote_scrub.py`, and two of five sampled modules have no name-matched test file at all (`usage_render.py` is covered by `test_cli_render_cost.py`; `process_group.py` by `test_process_group_kill.py`). `qt` wraps pytest-testmon, which records which tests executed which source lines, so it answers this mechanically: a leaf change reruns in 2.6s and an unaffected tree exits in 2.1s, against roughly two minutes for the suite. **Do not invoke `--testmon` by hand** — this repo's `addopts` carries a `-m` expression and testmon switches its selection off entirely whenever it sees one, so a hand-run `uv run pytest --testmon` runs the whole suite while looking like it worked. `qt` also falls back to the full suite for any non-Python change, because testmon cannot see into a subprocess and about sixty of this repo's test files drive a shell script or a binary rather than the product's own Python. It does not replace the full run before a commit; it replaces the several full runs you would otherwise do getting there. The suite itself has no headroom left — it is throughput-bound across every core, and measured, xdist's other scheduling modes are slower, gating the twenty slowest infrastructure files buys 4% of the wall time, and a fixture change that cut CPU 35% made wall time worse by trading cached work for disk I/O. Details in `docs/development/testing.md`.

Chain them in one shell invocation rather than one call each, and use `-x` / `--bail=1` while iterating so the first real failure stops the run. Drop the bail flag for the run you report, so its result covers everything it names. Never read the result through a pipe unless you know `pipefail` is on: a pipeline reports its *last* command's status, so `uv run pytest … | tail` exits 0 on a suite that failed. Set `set -o pipefail` in the same shell, or redirect to a file and check `$?` before reading it. **This is about your own shell, and it depends on who is reading.** A task running under the daemon inherits `SHELLOPTS=pipefail` from `executor.build_clean_env` and already has the option on (ISSUE-321); a person or an agent in a terminal in this repo does not, and neither does a `#!/bin/sh` script on Debian. Writing the option is right in every case and redundant in one. A run wrapped in `scripts/qtest` also says the answer in words, on stderr, which no stdout filter can drop.

**Wrap a full suite run in `scripts/qtest`.** Both suites size their worker pool from `cpu_count()` — pytest via `-n auto`, vitest by default — so each run claims the whole machine. That is correct for one run and pathological for several: work spread across worktrees means three jobs can ask for 36 workers on 12 cores, and runs then fail on timeouts that have nothing to do with the code. `qtest` is a `flock` semaphore holding one machine-wide slot (`QTEST_SLOTS` to raise it, `QTEST_TIMEOUT` to bound the wait, `QTEST_DISABLE=1` to bypass); it queues the run instead, so suites finish sooner and their results mean something. Serialize the expensive runs only — the fast feedback loop of a single test file needs no slot, and neither do `ruff`, `svelte-check` or `format:check`. **Every qtest run ends with one verdict line on stderr** — `qtest: PASS exit=0 time=3m41s cmd: uv run pytest`, or `FAIL`, or `KILLED-SIGKILL`, or `NO-SLOT` — because a pipeline reports the pipe's status and a failed suite then reads as exit 0. Read that line. stdout stays the command's own output, verbatim. Exit code 75 (`NO-SLOT`) means no slot came free and **the command did not run**; that is not a test failure. The lock lives in `~/.cache/qtest`, outside any repo, because the resource being shared is the laptop: other checkouts queue against the same slot by design.
