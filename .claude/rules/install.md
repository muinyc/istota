# The standalone install

The local single-user shape: what the wizard writes and what the updater does with it.

## setup_wizard.py

Interactive first-run installer (`istota setup`) for the local single-user shape. Two of the things it writes are boundaries rather than config. `ISTOTA_SECRET_KEY` is generated into `istota.env` and **carried forward on a `--force` re-run**, on the same rule Docker's `entrypoint.sh` applies to `/data/.secret_key`: every credential in the secrets table is Fernet-encrypted under it, so regenerating orphans the lot with no way back, and a re-run is a config rewrite rather than a key rotation. `ISTOTA_WEB_TOKEN_KEY` is carried with it and is the one to notice, because the wizard never *writes* one: `web_tokens.py` derives a second, independent Fernet from it for the `web_user_tokens` rows, so it is only ever present because an operator added it and the wholesale rewrite would delete a key with no recovery — carried forward, never generated, since that storage mode is opt-in. `ISTOTA_WEB_SESSION_SECRET_KEY` rides along for consistency, its loss being only invalidated cookies. **Two precedence rules decide *which* value is kept, and each is a way to write the wrong key into the file while looking correct**: the environment outranks the file, because `serve.load_env_file` is non-clobbering and an exported value is therefore the one actually in use (preserving the file's would write a value the daemon ignores, and the install would switch keys silently the day the export went away — the operator is told when the two differ, by name); and within the file the *first* line for a name wins, since `load_env_file` skips a name already in `os.environ`, so a duplicated `ISTOTA_SECRET_KEY` — precisely the shape an operator produces by appending the line a remedy told them to add to a file that already had one — must not be read as the later, dead one. Only a value meeting `secrets_store._MIN_KEY_LEN` is preserved, which is safe because nothing below the floor can have encrypted anything, and pinning a blank or truncated line would make the guard the bug. The env file is created `0600` through `os.open` rather than written and then chmod'd; the `fchmod` on the descriptor is the half that is easy to drop, since `O_CREAT`'s mode applies **only** to a file the call creates and the re-run is the one path where it pre-exists — so without it a hand-made 0644 `istota.env` is refilled with the master key at its original mode and narrowed afterwards, which is the same window on the only shape that has it. And it writes `{config_dir}/admins` naming the local user, pointed at by `ISTOTA_ADMINS_FILE` in the env file — an empty allowlist reads as "everyone" to `Config.is_admin` and as "nobody" to `is_shared_kv_writer`, so a standalone install with no file could not write a shared briefing block; the exemption in `is_shared_kv_writer` is the backstop for installs made before this, not the primary route. **It only ever creates**: an existing file is left byte for byte alone even when it does not name the user, and a line is printed instead, because the path is `config_path.parent / "admins"` with nothing asserting the standalone shape — `istota setup -c /etc/istota/config.toml --force` would otherwise append the wizard's user to exactly the file `load_admin_users` defaults to, a widening that survives the operator restoring `config.toml` from Ansible. Membership is asked of `load_admin_users` rather than re-parsed, so the writer and the reader cannot drift on what a line means

## updater.py

`istota update` — self-update for the standalone install: reads install.json provenance, git fetch/reset the recorded checkout (stable channel = latest release tag, main channel = branch tip), `uv tool install --reinstall`, fresh-code migrations. Refuses on the server shape
