# Web chat surface

The in-app chat surface in the web UI. Inbound/outbound plumbing is in
`.claude/rules/transport.md` (`WebTransport`); this file is the surface itself —
rooms, the composer, drafts, send durability, message actions, and the live
room-event stream.

## Overview

An always-on in-app chat surface in the web UI (full-page console at `/chat`, "Chat" nav tab before Feeds). Rooms are per-user channel tokens in `web_chat_rooms` (each gets its own `CHANNEL.md` + sleep-cycle handling); a sent message becomes a `source_type="web"` task (interactive: loads context + `CHANNEL.md` + `guidelines/web.md`) with `output_target="web"`, which routes as a stream surface (no Talk/email push — the result and progress live in `task_events`, tailed by the existing `/api/chat/tasks/{id}/stream` SSE endpoint). Endpoints under `/api/chat/*` in `web_app.py`: rooms CRUD (incl. `DELETE /chat/rooms/{id}` — a hard, token-scoped cascade across `task_events`/`tasks`/`web_chat_messages`/`channel_sleep_cycle_state` via `db.delete_web_chat_room`, guarded by `count_active_web_tasks` → 409 when a task is in flight, plus best-effort `Channels/<token>/` removal; channel `memory_chunks` are a documented residual — **and reached only for a room with no Talk conversation behind it**, since `web_app._is_talk_backed` sends any Talk-backed room down the per-user hide instead. That predicate reads the `talk` *binding* rather than `origin`, which is ISSUE-408: a promoted room kept `origin='web'`, took the cascade, and the cascade dropped `room_dismissals` with everything else while sending nothing to Talk — so the poll found the surviving conversation, registered it afresh, and the room came back with no memory of having been hidden. It reads the binding row and never probes Nextcloud, so a room whose conversation was deleted is Talk-backed too and can no longer be destroyed from web; "Reconnect to Talk" (ISSUE-401) owns that repair), message send/history, **`DELETE /chat/messages/{message_id}`** (see below), task confirm/cancel, attachment upload, and **`GET /chat/files?path=`** — the authenticated file handover. Web chat has no outbound attachment channel, so a file a task produces had no way to reach the user and the only answer was minting a _public_ Nextcloud link to hand someone a file they already own; this serves it inside the session instead (`_resolve_chat_file`), leaving link shares for giving a file to someone else. Confinement is two independent checks: the lexical one reuses the skill CLI's `resolve_scoped_path` (one rule for browser and model) and a `realpath` pass catches a symlink _inside_ the workspace pointing out. No admin bypass — `is_admin=False` always, since this is the most directly reachable read path on the web app. Always `Content-Disposition: attachment` + `nosniff` (the workspace holds user-authored HTML/SVG, which inline would execute on the app's own origin against the session cookie). An rclone deployment has no local workspace → 503 naming the share-link alternative. The model is told to use it by `config/guidelines/web.md`'s "Handing over a file" section — the surface guideline, not the skill, because the trigger is "a task produced a file" and `nextcloud` is a menu skill the model would never reach for on that prompt. Per-room UI: a kebab → `RoomSettings.svelte` modal renames a room (token invariant), sets its **standing model/effort default** (see below), copies its token (for a `web:<token>` route), and hard-deletes it behind a GitHub-style type-the-name confirm. **Per-room model default**: a room carries an optional `model`/`effort` on the shared `rooms` registry (canonical values, so the default is surface-independent — a Talk message and a web message in the same room resolve the same default). `transport.ingest.record_inbound` fills a task's model/effort from the room default when the message carried no inline `!model` override (the inline prefix wins as a unit — effort follows model, so an explicit model choice keeps its alias's own effort). Precedence: inline `!model` > room default > `config.model`. Settable on both surfaces via the `!room` command (`!room` shows current, `!room model <alias>` / `!room effort <level>`, `default` clears) and in the web room-settings modal (model + effort dropdowns fed by `GET /chat/commands`'s alias table; the PATCH validates against the brain's known models + effort levels and writes `db.set_room_model_effort`). Room-global by design — in a shared room one participant's setting applies to every sender.

**Room colour is the one per-room setting with no `!room` subcommand, and that is deliberate** (ISSUE-433). Every setting above is settable on both surfaces because it changes what the bot *does*, so a user on Talk must be able to reach it. A colour changes only how the web sidebar draws a row: Nextcloud Talk has no room colour to mirror (nothing in `talk.py`, `nextcloud_api.py`, `transport/talk/` or `provision_rooms.py` has a colour concept, and the only room attribute propagated to Talk is the name), so a `!room color` typed there would set a value its own surface could never render. It is also the first per-room setting that is **per-user rather than room-global** — it lives on the `web_chat_rooms` handle, not the canonical `rooms` registry, so two members of one shared room tint it independently and one member's choice is invisible to the other. Both halves point the same way, so the setting is web-only: the settings modal is the only writer, and `PATCH /chat/rooms/{id}` the only endpoint. `surfaces.py`'s room model has no presentation axis at all, which is consistent with keeping this off the canonical registry.

The palette is fixed and named (`src/istota/room_colors.py`, `web/src/lib/roomColors.ts`, token pairs in `tokens.css`), not a free-form colour: `web/AGENTS.md` requires every meaning-bearing colour to be defined in both theme blocks, and one user-picked value cannot read on both `--surface-raised` `#222` and `#e8e8ea`. The design linter could not catch that either, since `raw-color` scans source text and a hex arriving from the database is not source text. The route is therefore where a non-palette value is refused, and `tests/test_room_colors.py` holds the three spellings in step.

**Per-room brain**: `rooms.brain` rides the same lane, with three differences that all follow from a brain kind selecting an isolation posture rather than a preference. Writing it is admin-only (`config.is_admin`, keyed on the *presence* of the `brain` key so a clear is gated too — the existing `room.user_id != username` check is not the gate, since that is ownership of the per-user `web_chat_rooms` handle, which every member of a shared room has), the kinds on offer are the operator's `[brain] room_selectable` allowlist and the control is absent entirely when that is empty, and a pinned room gets no availability failover. `selectable_brains` is admin-only on the server rather than filtered in the component, so the client has one test instead of two that can disagree and a non-admin's browser never receives a list of kinds they cannot pick. **`brain` and `model` can arrive in one body**, which the modal makes the common case rather than an edge one, so the order is fixed: `_chat_update_room` applies the **brain first**, runs the namespace-clearing rule against the pin the room *already held* — by calling `commands._clear_pin_across_namespaces` rather than restating it — and then writes whatever the body explicitly chose. `{"brain": "native", "model": "vendor/x"}` therefore ends with both set, because the route validated that model against the brain the request is switching *to*; `{"brain": "native"}` over a room holding an anthropic id ends with the brain set and the model cleared, reported through `cleared: ["model"]` / `["model", "effort"]`. A value the body supplied is removed from that report, since it was replaced rather than lost — including an `effort`, which is a semantic rung every brain reads and is a fresh choice rather than part of the stored pair. That report is about this request and not room state, so the store strips it before merging and raises it as a notice.

That ordering is ISSUE-417's, and it reversed the original. `model` used to be applied first, so a model sent alongside a crossing brain change was written and immediately taken back out — which is why the modal used to **disable** its model and effort selects while an unsaved crossing change was pending, with `modelChanged` / `effortChanged` reading the same lock so the abandoned edit was not sent, and a caption telling the user to pick a new model after saving. There is no lock now: `GET /chat/commands` takes a `brain` parameter naming the kind the caller is *considering* (admin-only and allowlist-bounded, since the room still holds its old brain until the save lands), the modal refetches its list from the pending selection, resets a pin that cannot carry to "Default model", and the two go in one save. An id the incoming brain cannot run is a **400** rather than a silent clear — the picker offers that brain's own models, so that shape is a client bug rather than the ordinary edit it used to be. Rejected then and still rejected: 400 on the *combination*, which would make the modal special-case its own normal shape. The `cleared` notice still covers the case the modal cannot see — a brain moved from another surface between opening and saving. Rule and rationale in `.claude/rules/brain.md`. Deep link `/chat?room=<token>` selects a room on load (`selectRoomByToken`), silently falling back for an unknown/foreign token; the optional `&task=<id>` extension jumps to a specific turn after selecting the room (`jumpToTask` → pages up to 5 older history pages to locate it, scrolls the `data-cid`-anchored row into view with a ~2s highlight pulse). **`!search` result cards**: `cmd_search` returns a structured `command_data` payload (`kind="search_results"`) alongside its plain-text body via `CommandContext.result_data` → `dispatch` → the web POST; the store renders `SearchResults.svelte` (conversation cards carry a "Jump to reply" button = `jumpToTask`; memory cards show source + preview) instead of markdown, falling back to markdown for any other/absent `data`. Talk ignores `data` and keeps the text body + deep links. The read path (`commands._search_memory`) searches the `channel:{token}` namespace + all memory source types and classifies each hit on an `is_memory` axis (conversation rows room-scoped, recovering the room from the `messages` store via `db.get_message_room_for_task` past `tasks` retention); `cmd_search` runs a strict prefix pass, scope-filters, then retries once in OR mode only if the _scoped_ result is empty (forgiveness keyed on scoped emptiness, not global BM25 emptiness). The executor recall path + skill CLI keep strict AND (no prefix / no OR fallback) via unchanged `memory.search.search` defaults. `!commands` (and the `!model <alias>` prefix) work identically across surfaces — `commands.dispatch(... surface=...)` runs the handler over a `CommandContext` and delivers via the resolved transport on a push surface (Talk) or returns the text inline on a stream surface (web → `inline_result`); per-user rate limit counts `source_type='web'` rows in `tasks`. **Command autocomplete**: typing `!` in the composer opens a live-filtered dropdown of available commands (arrow-nav, Tab/Enter to accept, Escape to dismiss); `!model ` completes model aliases via the same mechanism. Built as a reusable prefix-autocomplete primitive in `web/src/lib/components/chat/autocomplete/` (a trigger-agnostic engine + per-trigger `CompletionProvider`s — `commandProvider`, `modelAliasProvider`) fed by one cached `GET /chat/commands` endpoint (`{commands, command_aliases, model_aliases}` serialized from `commands.COMMANDS`, `commands._COMMAND_ALIASES` and the active brain's `list_aliases()`, plus the admin-only `selectable_brains` / `brain_namespaces` / `inherited_brain` the settings modal reads — `brain_namespaces` covers every *known* kind and `inherited_brain` the one a room with no pin runs, because neither brain in a namespace comparison is necessarily on the menu — known rather than buildable since ISSUE-417, a namespace being a property of the kind rather than of the server's ability to construct it, which is also how `commands._clear_pin_across_namespaces` now answers). It also takes an optional `room_id` that scopes `model_aliases` to that room's own brain, which is what keeps the settings picker from offering a native room an anthropic id, and an optional `brain` naming a kind the caller is *considering* — the room holds its old brain until the save lands, so that is what lets the settings modal offer the incoming brain's models and save a brain and a model together (ISSUE-417). `brain` is admin-only and bounded by the same `room_selectable` allowlist the picker is, and an unlisted or unknown value falls back to the room's own brain rather than failing, since this endpoint's primary product is the command list. **The composer's own `!model` autocomplete still asks unscoped**, deliberately: the same response carries the command-name set the send path reads synchronously, and that set does not vary by room, so keying the whole catalogue by room would make the routing set depend on which room fetched last. An unrunnable alias typed into the composer is refused server-side against the room's brain rather than run, so the cost is a stale suggestion; adding a new trigger is a new provider, not a composer change. **Composer**: one bordered pill (`Composer.svelte`) holding `+` (file picker), the field, and two right-hand controls — Send, and beside it either the mic or, while a turn runs, Stop — see the two-buttons paragraph below; once the text wraps, the field takes the full width and the controls drop below it (a CSS `order` swap on a `multiline` class). **The send key is a bare Enter, and Shift+Enter writes the newline** — nearly every message is one line, so the unmodified key belongs to the common case; `Cmd/Ctrl+Enter` is kept as an alias rather than removed, since it was the send key long enough to be in people's hands. It is **gated on a hardware keyboard** (`usesSoftKeyboard()`, the same `pointer: coarse` primitive the post-send blur reads): on a phone there is no cheap Shift and the send button is already under the thumb, which is also why `enterkeyhint` stays `enter` — a soft keyboard is the only thing that reads the label, and it must not promise "send" where the key writes a newline. It sits **after** the autocomplete's own `onKeydown`, so a bare Enter accepts the highlighted completion while the popover is open and sends on the next press; the chord alone is checked ahead of the popover, being unambiguous. Making Enter the send key is what forced the popover to **decline a modified Enter** (`useAutocomplete.onKeydown`), which it used to swallow along with the plain one: Shift+Enter is now the field's only newline, so eating it left no way to break a line while a popover happened to be open.

**Two rules hold the send key together, and both were defects in the first cut of it.** Every keyboard path asks `wouldSend()` *before* consuming the key, so a key that cannot send falls through to the browser and writes its newline rather than being eaten — the send key going dead is the one failure the user has no way to read, and `preventDefault()` ahead of the gate produced exactly that during a running turn. `wouldSend()` collects four refusals: a **full send queue** (past `MAX_QUEUED_PER_ROOM` there is nowhere for the message to go, so the composer says so beside the field and leaves the text where the user can still see it), an **active recording** (the send button is deliberately swapped out for Discard/Finish and the field sits under an opaque overlay, so a key that sent would post text the user cannot see and strand the memo in the next message — a hole straight through a control that was removed on purpose), an **upload still in flight** (the file is part of this message; sending without it leaves the chip in the composer for whatever is typed next, which reads as the file having been sent), and `canSend`. The send button reads the same predicate, so the two cannot disagree about whether the message is ready. A running turn was the first of those four until ISSUE-238 and is no longer a refusal at all: the store queues what is typed against it, so the key does what it says and the queue's own cap is what replaced the gate.

**A message typed into a busy room takes one of two paths, and `runTurn` is what decides between them.** `runTurn`, not the server's task count, is the thing being protected: one non-re-entrant entry point holding `status`, the `pendingSend` echo slot and the pending-cancel flag, where a second concurrent call in the same room releases the first turn's frames before its task id is stamped. A `!command` is answered inside the request and comes back carrying no task id, so it never enters `runTurn` and takes nothing that belongs to the running turn — it goes out now (ISSUE-300). Anything else would be that second `runTurn`, so it is queued and re-enters through the same door when the running turn settles (ISSUE-238). The queue feeds the `status === 'idle'` guards rather than becoming an exception to them, which is why refusing the send was never the only way to keep the invariant. Note that "no task id" describes the *response*, not the server: `!retry`, `!resume` and `!confirm` each leave a task queued and still answer inline. Those turns arrive over the room stream and are adopted by `pickUpStreamedTask` exactly as a Talk turn landing mid-stream is, with the backend's per-channel gate serializing them — so they need nothing from this path, and the client deliberately does not try to claim them. What distinguishes a command from ordinary text is `isKnownCommand` (autocomplete `providers.ts`, off the same cached `GET /chat/commands` catalogue). That catalogue carries `command_aliases` beside `commands` (ISSUE-350), so the routing set is every name `dispatch` resolves, while the suggestion providers keep reading `commands` alone — the alias table stays out of `!help` and the popover, which is what it is for, without the client having to guess that `!inject` is a command. The catalogue is still the *only* evidence available client-side, which is the real reason an unregistered `!word` is refused — not that the server would make a task of it, since `dispatch` answers an unknown name inline too. What that refusal now costs is latency on a genuinely unknown name alone, and closing it would mean reproducing the `!model <alias> <prompt>` grammar client-side, which is a second copy of a server rule and the shape of the bug the alias set was widened to fix. Model aliases are deliberately not excluded from the set: the prefix resolved ahead of dispatch is the literal `!model <alias>`, not `!<alias>`, so an alias shadows nothing and filtering on one would only refuse a genuine command sharing a name with a role alias. `!model …` is refused on its own terms — no command is registered under `model`. **Before the catalogue lands the answer is no, and the queue changed what that costs**: it used to be a refusal the user could read, and it is now a command silently queued and answered as the *next* turn instead of this one, which for `!stop` or `!steer` is the opposite of what was typed. So `init()` warms the catalogue itself (`void loadCommandNames().catch(() => {})`) rather than leaving it to the autocomplete providers, which fetch on the keystroke that opens the popover and never at all for a pasted command. The composer holds no opinion either way any more — `isInlineCommand` went with the mode gate, and the rule lives only at the seam that owns the invariant: `send` routes a mid-turn command to **`sendInlineCommand`**, which writes no `status`, claims no `pendingSend` slot, does not reset `cancelRequested`, and withholds Retry for the reason `sendTurn` already does. An attachment disqualifies a command on both sides, since a file belongs to a task.

**Two things that exemption breaks if they are not handled, both found in review.** A command may write a **durable `messages` row** — `cmd_steer` records the note as a `task_id IS NULL` user row, the same shape a confirmation answer takes — and that row echoes back over the room stream carrying no task id, so `msg_id` is the only dedup key `appendStreamedRow` has. `cmd_steer` therefore returns `{kind: 'steer_recorded', user_msg_id, body}` on `result_data` and `applyInlineResult` stamps it, exactly as `confirmation_answered` already did; `body` rides along because the stored row holds the note alone while the client drew the whole `!steer <note>` line, and adopting it is what keeps the live transcript and a reloaded one identical. Unstamped, the steer renders twice live and once after reload. This was unreachable before: with the room idle `cmd_steer` refuses and writes nothing, so the branch was dead on this surface.

And **two sends can now be open in one room**, which the draft machinery was not built for. `unsettledSends` is keyed by draft key — one entry per room — on the reasoning that the mode gate standing here until ISSUE-238 allowed one open send per room and a second could only be another room's. A command sent while an ordinary message is still pre-ack breaks that: it would overwrite the map entry and the stored draft, and its own ack would then clear the draft belonging to the message still in flight, which for a send that goes on to fail is the only copy that survives a reload. Two halves close it. `submit` writes the *held* text back rather than its own when an unsettled send already owns the slot — a command is not a draft worth restoring. And `settleSend` splits: `sendInlineCommand` calls `settleSendRow`, clearing its own row's marks without bumping `sendSettled`, since only a drafted send may signal an ack the composer will act on.

One smaller consequence outlived the gate, and the queue is what made it worth fixing. The hidden aliases in `_COMMAND_ALIASES` (`!yes`, `!inject`, …) are not in `COMMANDS`, so while the endpoint served `commands` alone `isKnownCommand` said no to all of them — including `!inject`, which is `!steer`'s own alias. Mid-turn they were refused outright under the mode gate, and once the queue replaced it they were queued and went out as the *next* turn: the server resolved the alias and answered inline, but by then the room was idle, so `cmd_steer` reported no running task to steer. Late rather than lost, and for `!inject` late reads as a refusal of a command that was valid when it was typed. `GET /chat/commands` now publishes the table as `command_aliases` and `isKnownCommand` reads both halves (ISSUE-350). The other direction of losing `isInlineCommand`: a `!command` is refused by `wouldSend()` while `queueFull` is true, which takes ten messages queued in a busy room to reach and is one Remove away from clearing.

**The send queue is per room, keyed by token, and holds messages that have not been POSTed at all** (ISSUE-238). Keep its vocabulary apart from `streamQueue`, which holds assistant placeholders whose tasks the server already has: `sendQueue` / `enqueueSend` / `drainSendQueue` against `streamQueue` / `enqueueStream`, and a queued *user* row reads "Waiting to send" where a queued assistant placeholder reads `Queued…`. By token rather than room id for the reason `drafts.ts` gives — `web_chat_rooms.id` is an `INTEGER PRIMARY KEY` without `AUTOINCREMENT`, so a deleted room's queue would be inherited by whichever room takes its id next. The entry is the source of truth for what will be sent and the transcript row is a mirror for display, which is why nothing on the drain path reads the payload off the row: a room switch takes the row off screen while the entry stays. There is deliberately **no server-side queue** — posting straight away would work, since the backend's per-channel gate serializes tasks, but it commits the message before the user has decided it should go, which costs the edit and the remove, turns Stop into "cancel these too", and mirrors the text into Talk while they are still deciding.

**A drain re-tests everything and sends one entry.** `canDrain` wants the `room` view on this room, a reachable server (`online`, ISSUE-202 — draining into a gap just manufactures one 30s stall per message for an answer the store already has), `status` idle with no `activeStream` and an empty `streamQueue`, no row mid-`sending`, and an unheld head; a drain that is not allowed is a silent no-op rather than an error. **The entry stays in the queue until the POST is acked** (ISSUE-202, reversing ISSUE-238's shift-before-POST): an ack removes it, an `unreachable` or `timeout` leaves it exactly where it is and parks the row back to `queued`, and a `rejected`-class failure removes it and fails the row. The early shift traded a duplicate for a loss, and the duplicate it was avoiding can no longer happen — `idempotencyKey` is minted at enqueue and the server answers a replay with the first task, so a force-quit between the POST and the ack re-sends and resolves to one turn rather than losing the message. The entry is handed to `beginSend` — the prelude extracted from `retrySend`, so both re-enter `runTurn` with the same cid and the echo dedup in `appendStreamedRow` folds the canonical row into the bubble already on screen. The next entry goes when *this* turn settles.

**An entry carrying files uploads them first, one at a time, and the POST is the second step** (ISSUE-202). An attachment written with no connection has no host path to reference, so the entry carries a `PendingAttachment` per file while the bytes live in the `blobs` object store in IndexedDB, and `beginSend` resolves them ahead of `runTurn`. The entry is re-persisted after each upload lands, before the next starts and before the blob is deleted, so a drain interrupted halfway resumes at the file that has not gone rather than re-uploading one the server already has — which is why `attachments` and `pendingAttachments` are two fields kept in step (every chip with a null `path` carries a `pendingBlobId` with exactly one record behind it) and why a *half*-resolved entry has to read back as valid. `readEntry` refuses an entry whose two halves disagree, because a null path would be POSTed as a file the server cannot resolve. Three outcomes ride on that step and they are the send's own three: a gap leaves the entry and its bytes where they are and parks the row, a refusal fails the row with the server's reason and drops its bytes (no Retry — a retry cannot change a verdict on a file), and bytes that are simply gone fail the row rather than sending a message stripped of the file it was written about. That last one is the only place a row fails without the server having been asked anything. The room is claimed (`status` `'sending'`) for the length of the uploads, exactly as `runTurn` claims it for the POST, and a Stop tapped during one holds the entry rather than being swallowed. A **session-local claim set keyed by cid** is what stops a second drain of the same entry: the row's own `'sending'` mark is not enough, because a `'sending'` row is not client-only and a room switch drops it, after which the rebuild paints the entry as `queued` again and `loadHistory` drains at its foot. Nothing makes an upload idempotent the way the idempotency key makes the POST idempotent.

**Bytes are bounded where they live, references where they live.** `MAX_PENDING_BLOB_BYTES` (10 MiB per file), `MAX_PENDING_BLOB_TOTAL` (50 MiB across the store) and an 80% `navigator.storage.estimate()` headroom check are applied in `offline/db.ts` before the write, and the composer reports all three as one sentence — from there they are one fact, and eviction is whole-origin, so a file that fills the quota takes the text queue and the transcript cache with it. The queue's own `MAX_QUEUE_TOTAL_CHARS` charges an entry for its `PendingAttachment` records and not for the bytes. Blobs are collected on `init()` by a rule of their own — unreferenced by any live queue entry *and* older than an hour — the age floor being what stops it racing a file staged in the composer and not yet sent, and the reference set is read from storage as well as memory since `restoreQueues` leaves another user's entries and any naming a room this user no longer has exactly where they are. The composer drops the bytes behind a chip it clears itself (a removed chip, a room switch), because the queue is what the collector reconciles against and those files were never queued.

**Five triggers, where the spec's own list had three.** `onStreamSettled` on a `done` terminal is the ordinary one. The second is `loadHistory` rather than `selectRoom`, deliberately one level down: `init()` calls `loadHistory` directly and `recoverStream` rebuilds through it after a stale reconnect, and that path halts the active stream first, so `settle` early-returns on `finished` and `onStreamSettled` never fires for that task — at `selectRoom` an entry was stranded with no trigger left, which an alt-tab past `ROOM_STREAM_STALE_MS` during a long turn was enough to produce. `releaseQueued` is the third. The last two are the paths where a send produces no stream to settle at all: `sendTurn`'s inline return (`task_id == null`, which any `!word` the client's catalogue does not carry can reach) and the end of `sendInlineCommand`.

**The hold rule is one sentence: the queue drains when the turn it was written against finished normally, and holds otherwise.** `error`, `cancelled` (Stop), a turn parked on a confirmation and a failed send all set `held` on every entry in that room, and a held row reads "Held — not sent" with a Send control. Holding rather than discarding is the trade the issue's own Direction got half right: the follow-ups were written against work the user has just abandoned, so they must not fire, but deleting the text to say so costs more than the tap to release it. Two placements decide whether the rule actually holds. The hold is applied **above** the stream-queue advance in `onStreamSettled`, because a room can carry two live tasks (an adopted Talk turn, or two resumed from history) and a second task waiting its turn returns early below — so one turn's Stop has to mark the entries before the *next* turn's `done` releases messages written behind the abandoned one. And `failSend`'s hold is gated on `settleStatus`, false only for an inline command failing alongside a turn that is still going to finish normally: unconditional, a failed `!command` held everything queued behind a healthy turn, and the hold then meant that turn's own `done` drained nothing.

**Three verbs on the session, all no-ops on a cid that is not queued.** `removeQueued` drops entry and row, orphaning its uploaded attachments the way closing the tab mid-compose already does. `editQueued` is remove-plus-restore rather than an in-place editor on the bubble: it hands text, attachments **and the citation** back through the existing `sendReturned` store, which the page already guards on the room token — and it refuses up front when the entry is not the active room's, because the destructive half runs before that guard could stop it and `findQueued` scans every room's queue by cid. `releaseQueued` clears one entry's hold and attempts a drain; only the head can go, so releasing an entry behind a held one marks it ready and sends nothing yet.

**A queued row is a client-only row, like the stranded failed row ISSUE-200 left behind** — `isClientOnly = isStranded || isQueued` is what `stashStrandedSends` and `carryClientOnlyRows` work on. Queued rows are skipped in the `token === null` branch (the All view), which spans every room and has no composer for a per-row action to act against; failed rows keep their existing behaviour there. `stopActive` still abandons `pendingSend` and clears `streamQueue`, and deliberately leaves `sendQueue` alone — nothing in it has been sent, so there is nothing to abandon, and the rows come back with the room. `forgetRoom` is the single place either class of client-only row is dropped *because its room went away*, and it drops the in-memory queue with them (`removeQueued` and `editQueued` take an individual entry out through `takeQueued`, which is a different question); the *stored* copy goes only on a real delete (`dropRoomQueue` from `deleteRoom`, plus the page's own `dropQueue` beside `dropDraft`), because an archived room or a room list that came back short must not cost committed text.

**The client-only rows hold the bottom of the transcript, and every other append goes above them** (ISSUE-351). A queued row has not been POSTed and a stranded failed one never was, so both are pending actions rather than events in the history: they carry Send / Edit / Remove or a Retry, they belong against the composer, and a server row landing under one reads as the answer having come before the question. `appendAboveClientOnly` is the walk that enforces it — it was `loadHistory`'s resume splice, and being written at one call site rather than at the seam is the whole of what went wrong. Eight appends go through it now (`send`, `sendTurn`'s placeholder, both of `sendInlineCommand`'s rows, `appendStreamedRow`, `pickUpStreamedTask`, `feedAggregateView`, and `loadHistory`'s own resume placeholder); `enqueueSend` and `appendQueuedRows` keep their plain tail pushes, since they *are* the block being walked past, `loadOlder` prepends whole pages at the head, and `carryClientOnlyRows` already re-appends the block at the tail on every rebuild. **The widest case was the ack window and it is not narrow**: `sendTurn` appends the placeholder on the ack, so a message queued while that POST was still open used to land above it and the running turn's whole answer streamed in underneath the message waiting on it — a POST that goes out while the daemon is already running a task can sit behind SQLite write contention for seconds.

Three consequences are deliberate rather than overlooked. A mid-turn `!command` sorts **above** a message queued before it, a departure from strict chronology and the point of the rule — the queued row has not happened yet. A drained row needs no special case: `beginSend` stamps `'sending'` before the POST, so it stops being client-only where it sits and its own placeholder lands directly under it. And **the rule holds at append time only**: `beginSend` and the failed-send adoption both settle a row in place, so a stranded failed row sitting *above* a queued one is left above a live turn once that queued one drains, until the next rebuild puts it back at the tail. That is the pre-existing behaviour and it stays — the row above is still the Retry the user wants, and repositioning a bubble on settle moves it out from under the pointer already heading for it.

**The block is outside the transcript's chronology, which the day dividers have to know.** A queued row is stamped when it was typed and a *restored* one keeps that stamp for up to `QUEUE_TTL_MS`, so pinning the block below every server row puts an older timestamp at the bottom — and `startsNewDay` in `routes/chat/+page.svelte` is pure adjacency, so it drew "Yesterday" underneath today's conversation and the transcript read as running backwards. A client-only row draws no divider. That is why `isStranded` / `isQueued` / `isClientOnly` live in `stores/segments.ts` rather than inside `createSession`: the page needs the same predicate the store orders by, and two spellings of it would disagree exactly where this bites.

**Persistence is `stores/sendQueue.ts`, shaped like `drafts.ts`** — one `localStorage` map under `chat.sendQueue`, keyed `<user>:room:<token>` for both the reasons the draft key gives. Storage mirrors memory: every mutation that changes what the queue holds writes its own room out, and `writeQueue`'s clamped return is deliberately *not* adopted back, since a storage bound trimming the live queue would delete a message the user can see on screen. **Two mutations deliberately do not write back, and both matter to whoever reads that rule as absolute.** `forgetRoom` deletes the in-memory queue and leaves the stored copy alone on purpose — persisting there would destroy committed text on an archive or a remote `remove` frame, which is the whole reason `dropRoomQueue` is a separate call reached only from `deleteRoom`. `restoreQueues` is the other, below. Bounds are `QUEUE_TTL_MS` (7 days, shorter than the draft TTL because a queued message is a pending action rather than half a thought), `MAX_QUEUED_PER_ROOM` 10, `MAX_QUEUE_ROOMS` 20 evicted oldest-first, `MAX_QUEUE_CHARS` = `MAX_DRAFT_CHARS`, and `MAX_QUEUE_TOTAL_CHARS` 256 KB counted over the *serialized* entry rather than its text alone, which is what the quota charges for. The per-room cap is enforced at `enqueueSend` as well as in storage, and that pairing is the point: `prune` keeps a room's FIFO **head**, since that is what drains next, so an eleventh message accepted into memory would sit on screen looking queued while the copy that survives a reload was the one silently dropped. The composer's own `queueFull` refusal sits on top and is the better one, because it keeps the text in the field rather than in a notice.

**The store needs a user id it did not have, and it rides down on the config.** `GET /chat/config` publishes `user_id` and `init()` stashes it before anything else, which is what makes restoration ordered — the page's `getMe()` resolves after `init()`, so a key pushed down from there would have an ordering hazard exactly where restoration happens. Until the id is known the queue is in memory only and nothing is written. `web/vite-mock-api.ts` carries the field too, or the persistence half is silently off on a dev server.

**A restored entry is re-minted a fresh cid, and whether it comes back held depends on why it was queued** (`holdOnRestore`). A `busy` entry is always held: the turn it was written against is over and unobserved and the user is not watching the room they wrote it in, so firing it on page load is the one surprise a send queue must never produce; it comes back reading "Held — not sent", one tap from going out. An `offline` entry (ISSUE-202) is the opposite case — going out by itself when the connection returns is the whole of what it is for, and a relaunch is exactly the moment that has to work — so it comes back ready, up to `OFFLINE_AUTO_SEND_MAX_AGE_MS`, past which the hold is the better answer again. **A hold the previous session applied is kept whatever the reason says**: Stop, an error and a parked confirmation mark every entry in the room through `holdRoomQueue`, offline ones included, so the age rule can only ever keep a hold and never clear one. The cid is re-minted because `cidCounter` starts fresh on every load and the stored value would collide with a row this session is about to make — a cid is a client-local display key, not durable identity, and `idempotencyKey` is the identity that survives the round trip (minted at enqueue, so two drains of the same restored entry are answered with one task). `restoreQueues` skips a token already live in memory, since `init()` runs again on every remount while the session outlives it and storage is this map's mirror; it skips any stored key not under this user's own prefix, since a browser profile two people take turns using holds both their queues under the one storage key; and it leaves a key naming a room this user no longer has alone rather than dropping it, because an archive or a short room list must not cost the text. It is the second exception to the mirror — it does not write back, which would rewrite the whole map on every page load for rooms nobody has touched, and nothing depends on it because every restore re-mints and re-holds unconditionally.

**The composer is two buttons now, one meaning each.** Send is always Send; Stop is its own control, rendered *before* Send inside `.tools` (which is `margin-left: auto`), so a row that grows grows leftwards and Send never moves under a thumb. That retires the mode flip, `MODE_FLIP_GUARD_MS`, `lastActivationAt`, `lastActivationMode` and `activatePrimary` together: the single two-mode control existed because an `{#if}` swap destroys the element a tap is still resolving against, the flip inside one element was the mitigation, and the guard window was the mitigation's own mitigation. One button per meaning cannot be tapped for the meaning it no longer has. `showStop` survives as the name of a plain `busy && !!onCancel`, and the mic is gated on `!showStop` so Stop takes its slot rather than a slot of its own. That last part is a layout constraint, not a view about the mic: `singleRowWidth` subtracts `.tools`' measured width to decide where the text wraps, and a wrap is what moves the field onto a row of its own with the controls underneath — so a third button mounting at turn start narrowed the field by 2.7em and put the whole composer on two rows for the length of every turn. Two buttons in both states keeps that width fixed. The residual is a browser with no `MediaRecorder`, where the idle row has one button and the shift returns; `Composer.sendButton.svelte.test.ts` pins the count with the mic faked in, since jsdom has none and the assertion is otherwise vacuous.

**`queueing` decides who holds the durable copy of the submitted text, and it has to be read before `onSend`.** An ordinary send has no durable copy until the backend acks, so the draft is held through the ack; a queued one is written to its own persisted queue as it is accepted, so the draft is dropped there and then and no `unsettledSends` entry is written — which also sidesteps that map's one-entry-per-key limit, since several queued messages in one room would otherwise fight over the slot and the first ack would drop the last one's stored copy. The prop is captured into a local at the top of `submit()` because `onSend` runs `send()` synchronously through `status.set('sending')`, so `busy` — and with it this prop — has already flipped by the time the draft branch is reached. Read there, every ordinary send from an idle room took the queued branch: the draft cleared on submit, no `unsettledSends` entry, `settleDraft` and `switchDraft`'s in-flight refusal both inert, and nothing saying so. Two things it cannot distinguish, both accepted rather than overlooked: a mid-turn `!command` arrives as `true` and has its draft cleared though it is queued nowhere (the alternative is an `unsettledSends` entry no ack ever settles, since `sendInlineCommand` does not bump `sendSettled`), and an enqueue the store *refuses* — a room that left `$rooms` mid-click — has already lost the text from the field, which closing means `send()` reporting acceptance.

**`queueFull` is gated on `busy`, and the gate is the whole of it.** `send()` reaches `enqueueSend` only while `status !== 'idle'`, so the cap applies only to a busy room. Derived from the queued-row count alone it disabled the composer entirely in an idle room whenever ten rows were on screen — which is exactly what a restored queue looks like on page load — under a notice about messages waiting on a turn that was not running.

**The queued bubble renders its body in full and mutes it.** Text, attachment chips and the optimistic reply quote are all there, because the point of the row is that the user can see what they committed to sending; `.msg.queued` drops those three to `opacity: 0.65` while the status line and its buttons stay at full contrast, since they are what you act on. The line reads "Waiting to send" or "Held — not sent", with **Send** (held rows only — an unheld entry drains by itself, and a button that fired it early would race that drain for the one slot `runTurn` owns), **Edit** and **Remove**, wired to three optional props absent on read-only surfaces exactly as `onRetry` is. Edit and Remove are `IconButton`s — a pencil and an X, `sm` so they take the same box as Send's `Button` — because the status line already carries the sentence and two more words after it read as part of it rather than as controls; their `aria-label` is the whole of their name, so a test asserting on this row reads accessible names rather than `textContent`. Remove takes `danger` and an X rather than the turn row's `Trash2`: deleting a turn removes something every member can see, while this discards something that never went out. Send keeps its word — it is the one that acts on the world, and it appears only where it is the decision being offered. `hasRowActions` excludes a queued row for the reason it excludes a failed one: copy, star, reply and delete all act on a durable turn, and this is not one yet.

**The IME guard is two mechanisms, because the event alone cannot answer the question.** `isImeComposing` (`$lib/platform/input`, shared with the room-name field on the chat page, which has the same hazard) tests `isComposing` and the legacy `keyCode === 229`; on top of it the composer keeps a `compositionend` timestamp and treats an Enter within `IME_COMMIT_GRACE_MS` as the input method's, because WebKit can dispatch `compositionend` *before* the keydown that confirmed the candidate, which then carries neither mark. The check is hoisted to the top of `onKeydown` rather than repeated per branch: the popover navigates on the arrow keys an IME uses for its candidate list, so it is a precondition of the whole handler. Two further non-obvious invariants. (1) **Wrap detection is measured at the single-row width, never the field's current width** — wrapping moves the controls out of the field's row, which widens the field, which can un-wrap the text, which flips it back; measuring the live width makes the decision depend on its own output and the field alternates one/two rows on consecutive keystrokes. `wrapsAtSingleRowWidth` pins the _wrapper's_ inline `flex-basis` for the measurement (the field is a flex item with `flex: 1`, so its own `width` is ignored for sizing), and height sizing is a separate pass after `await tick()` so it measures the width the field ends up with. `<svelte:window onresize>` re-evaluates, since the wrap point moves with the container. (2) **Control sizing is `em`-relative with `font: inherit` on the buttons** — a `<button>` does not inherit font, so without it the `em` sizes resolve against the UA's ~13px and the controls stay fixed while the text-size preference scales the type around them. Voice messages: `useRecorder.svelte.ts` wraps `getUserMedia` + `MediaRecorder` (webm/opus on Chrome/Firefox, `audio/mp4` named `.m4a` on iOS) and hands the result to the ordinary attachment upload — `executor._pre_transcribe_attachments` transcribes any audio attachment into the prompt, so this needs no dedicated endpoint (needs the `whisper` extra; `webm` is in `attachment_extensions`). The mic hides itself when `navigator.mediaDevices` is absent, which is what makes it disappear outside a secure context rather than failing on tap. Stored attachment names lead with a sanitized stem (`_attachment_stem`, `[A-Za-z0-9._-]` only, `Path.stem` drops any directory component) plus a random suffix, so the inbox is browsable without trusting a client-supplied filename. **Attachment chips are persisted, not just optimistic**: a turn's chip labels live on the canonical `messages` row (`messages.attachments`, JSON display names, written by `record_inbound` via `transport.display_attachment_names`) and are emitted on every user-row history/stream payload. They used to exist only in the composer's in-memory file list, so leaving a room and coming back silently dropped the record that a file was part of the turn. The names are duplicated off `tasks.attachments` (paths) deliberately — retention GCs the task row, while the transcript has to keep showing the file; a turn predating the column falls back to basenames of the joined task paths. The client supplies the display names (`attachment_names` on the send, positional, discarded wholesale on a count mismatch) because the _stored_ filename carries the collision suffix above — a basename-derived chip would read `note-a1b2c3d4.txt` where the live one read `note.txt`. Every other surface (Talk) falls back to the basename, which is also what gives a Talk-attached file a chip in web chat. **A chip is also a link to the file it names** (ISSUE-206), pointed at the same session-scoped `GET /chat/files?path=` handover described above — the user opening a file they already own, so nothing becomes public. A minted Nextcloud share link is the wrong tool here for the same reason it's the right one for handing a file to someone else. The link needs a _workspace_ path (`/Users/<uid>/…`) while the attachment is stored as a host path, so `transport.ingest.workspace_attachment_paths` translates once at ingest and the result rides the message row as `messages.attachment_paths` — a JSON array positional against `attachments`, stored beside the names for the same reason they are (the host paths live only on the `tasks` row retention deletes, so deriving at read time would make every link rot after a few days). A `null` entry means "not servable" and renders the inert chip it always was: a Talk attachment lives under `/Talk`, and a mountless (rclone) deployment has no local workspace at all. The read path re-scopes to **the caller's own** workspace rather than trusting the stored value, because rooms are shared — a co-member sees the chip but `/chat/files` would refuse them the file, and offering a link that 403s is worse than offering none. `POST /chat/attachments` returns `workspace_path` alongside the host `path` so the composer's optimistic chip is a working link immediately; without it the just-sent chip would stay inert for the whole session, since the optimistic row is deduped against the streamed echo rather than replaced by it. **Attachment intake.** Five entry points through one `upload()` sink in `Composer.svelte`: the `+` menu's three native rows (photo library, camera, document picker — shell 0.3.0), the plain file input off-shell, paste, drop, and the voice recorder. The server publishes its own limits at `GET /chat/config` (`max_attachment_mb`, `attachment_extensions`) and the composer pre-checks against them, **fail-open** — `limits` stays null until the config lands, so an unreachable endpoint never becomes a client-side refusal and the server's 413 is the backstop. The app default is 25 MB but the Ansible role deploys **100** and renders nginx's `client_max_body_size` from the same variable; splitting them means nginx answers its own HTML error page, which the client cannot parse (`uploadFromShell` tolerates that shape deliberately). `heic` is in the accepted set because that is what an iPhone photo is — the gallery picker usually re-encodes to JPEG, but a HEIC dragged off a Mac was being refused on extension. A native-picked file need not enter the page at all: with `IstotaUploader` present the shell posts it straight from disk with URLSession (absolute URL, `file` field), and otherwise the file is read in 3 MiB windows into a `File` backed by the WebKit blob store rather than the JS heap — which is what made the client-side ceiling removable. The temp copy is deleted on every path. A send with **no text** is accepted when attachments are present; `_describe_attachment_only_message` stores a descriptor as the prompt ("Voice message (see attached audio)." for an all-audio turn) so the transcript, the LLM context and the Talk mirror all read something. Relatedly, `_pre_transcribe_attachments` now **appends** a transcript rather than replacing the prompt — text typed alongside a voice memo used to be discarded. **Drafts** (ISSUE-205): unsent composer text survives leaving the room and leaving the page, held client-side in `localStorage` (`stores/drafts.ts`, one map under `chat.drafts`) rather than round-tripped through the server — a draft belongs to the machine it is being typed on, and publishing text the user has not decided to send is the one thing a draft is not. The page hands the composer a `draftKey`; without one the field behaves exactly as it did. The key is `<user>:room:<token>`, and both halves earn their place: the **token** rather than the room id because `web_chat_rooms.id` is `INTEGER PRIMARY KEY` **without** `AUTOINCREMENT`, so SQLite hands a freed rowid straight back out and a deleted room's draft would be inherited by whichever room takes its id next; and the **user** in front of it because a shared Talk room has one token across every member, so on a browser profile two people take turns using, a bare token would hand one person's half-written message to the other. The composer is mounted once and never keyed on the room, so before this a draft did not merely vanish on a tab switch — it also followed you into the next room; `switchDraft` writes the outgoing room's text down before restoring the incoming one's, which closes both halves at once, and clears the attachment chips on the way (they are not drafted, an uploaded file being server-side already, but re-picking one costs a tap while posting it to the wrong room does not undo). Writes are debounced (`DRAFT_SAVE_DEBOUNCE_MS`) with an immediate flush on every departure the component can see: a key change, unmount, `pagehide` (a reload or a close — the event a WKWebView delivers where `unload` is not) and `visibilitychange` → hidden, which is the **only** callback a backgrounded iOS app gets before the page may be discarded; without that one the exposure is 400ms of _idle_ rather than of typing, since continuous typing never reaches a debounce. **Two null-key cases that look identical from the prop and want opposite treatment.** Text typed before the room list answers is carried into whichever room lands, since there is no earlier room to attribute it to — but a stored draft always outranks it, or one keystroke during that window would destroy the draft the user came back for. A key going null _later_ means the room was deleted, archived or removed by another client, all of which leave the view on `room` with the composer mounted; there the field is cleared, because carrying that text is exactly the leak. The carry is therefore gated on a one-shot "has ever had a key" flag, not on the previous key being null. Bounded by a 30-day TTL (checked on read as well as on write, so an expired draft is never restored) and a 50-entry cap, because a room that is deleted or never revisited would otherwise leave its draft behind forever and nothing else collects it; writing an unchanged draft is a no-op so that merely _visiting_ a room neither re-serializes the map nor pushes its age out. **Two further bounds exist for a different reason — size rather than collection** (ISSUE-216). Because every draft shares one storage entry, every write serializes the whole map, so one entry large enough to exceed the origin's quota made the write fail for _every_ room at once — and `persisted.ts` swallows that, so nothing was saved and nothing was reported, which is right for a preference and wrong here. A paste is the ordinary way past it. So one draft is capped (`MAX_DRAFT_CHARS`, 64 KB, kept deliberately above the server's own `max_prompt_chars` so truncation can only reach text that could not have been sent) and the map as a whole is capped (`MAX_DRAFTS_CHARS`, 256 KB, counted in characters of draft text rather than in the code units the escaped payload costs). The per-draft cap is applied **on read as well as on write**, so a map written before the caps existed is healed on first read rather than carried back into a write at full size; the whole-map cap is applied in `prune`, where the map is assembled, and evicts oldest-first like the entry cap. `prune` takes the key currently being written and moves it to the front, because two writes in the same millisecond tie and a tie resolves to insertion order — so without it the entry a caller just wrote could be the one evicted, the single outcome no caller can work around. **`writeDraft` returns what was actually stored, and a caller holding its own copy must keep that rather than what it passed**: the composer records the submitted text to recognise it again when the send acks (`settleDraft`) and to refuse restoring it mid-flight (`switchDraft`), and comparing a full-length copy against a clamped stored one makes both tests miss — which leaves the draft behind for good and puts an already-sent message back in the field as unsent text. Neither cap makes a refusal impossible: the quota belongs to the origin, and a refusal originating anywhere else is still silent.

**Send lifecycle on the user's own row** (ISSUE-200). The composer used to append the user turn and an assistant placeholder optimistically and then POST — so a message had exactly one appearance whether or not it ever reached the backend. Worse, the one failure that was handled (an HTTP error response) was written into the *assistant* placeholder, which made "your message never left" present as "the assistant errored replying", and the failure the issue actually reports took a path with no handling at all: `fetch` **rejects** rather than resolving when the backend is unreachable, so the throw escaped an un-awaited caller, `status` was never reset off `'sending'`, and the composer stayed showing Stop with no way to send until reload. The ack itself already existed — the endpoint returns `{task_id, status: "pending", …}` — and is unchanged; this is entirely client-side. `sendChatMessage` now **classifies instead of throwing** (`SendFailure` = `unreachable | timeout | auth | rate_limit | rejected`, plus a `SEND_TIMEOUT_MS` bound `fetch` has none of), the row carries a `sendState` lifecycle, and `failSend` **removes** the assistant placeholder rather than repurposing it — the turn produced no assistant message. Absence of `sendState` is the settled state, deliberately with no `'sent'` member: every row rebuilt from history is settled by construction, and the ack's visible form is the pending mark clearing rather than a receipt we have no read-receipt semantics to back. Four non-obvious constraints. **Retry reuses the failed row's `cid`**, because `appendStreamedRow` dedups on `(role, task_id)` — stamping the retry's new id onto the existing row is what folds the canonical echo into it, where appending a fresh row would leave the failed one behind and show two bubbles for one message. It therefore needs the original `ChatAttachment[]` stashed on the row (`sendPayload`): the rendered row holds display names and *workspace* paths, not the host paths the POST body takes. **Retry is gated on an idle status** (and its button disabled while busy) because `runTurn` is not re-entrant — it drains the `pendingSend` echo buffer on entry and silently resets `cancelRequested`. `send` was gated by the composer's `busy`; Retry was the first entry that wasn't. Since ISSUE-238 neither is gated there — `send` branches on `status` itself and queues what it cannot pass through — while Retry keeps its own idle check and stays out of the queue, a recovery of one specific failed row having no obviously right position in a FIFO of messages not yet sent. **A send the server accepted but never got to report** — a client timeout, a socket dropped after the request was processed — leaves a row marked failed whose task is really running; `appendStreamedRow` reconciles that by **adopting** an echo whose `(role, text)` matches a failed, task-less row instead of appending it, matched on the body precisely so a send the server rewrote (an attachment-only descriptor, a stripped `!model` prefix) falls through to the old duplicate rather than claiming a wrong row. **A row the server attributed to somebody else is refused before the body is compared at all**: a room is shared, so a co-member typing the same words while this client holds an unsent row was folded into it, and since the adoption writes no author the row went on reading as the viewer's own — the wrong name while a user row named no writer, and the reader's own face over another member's words once `author_id` was on the wire. Both fields are tested, since an external sender carries a label and no id. That heuristic is now the fallback rather than the mechanism (see `client_msg_id` below), and is what still covers rows created before the key existed. **`failSend` only sets `'idle'` when its turn's room is still on screen**: switching rooms isn't gated on `busy`, so a send failing after a switch would otherwise unlock the composer over a room with a live stream. Retry is withheld where it cannot succeed — an expired session, and any other 4xx that is a verdict on the request (409 archived, 400 over-cap, 413) — mirroring the server's own transient/permanent split. Per `web/AGENTS.md`, a *classified* send failure is **in-band** and raises no `notify()`; the two `notifyError` calls on the send path are last-resort catches for a rejection that escaped the store's own handling, where a notice beats silence. An offline outbox is deliberately out of scope and belongs to ISSUE-202, whose queue plugs into this same `sendState` union.

**One progress indicator per turn, handed over at the ack.** The grace-gated pending mark and the assistant placeholder's ack verb are the same claim at two phases of one turn, and both used to render: the placeholder was appended before the POST went out, so any send outliving the 400ms grace showed `Sending…` on the user row and `Sleuthing…` below it simultaneously — with the assistant one asserting the model was working on a message that had not reached the server. A `!command` made it deterministic rather than occasional, since it runs *inside* the request (`res.task_id == null`) and holds the POST open for the whole command; `!search` over a memory corpus is seconds of it. `runTurn` therefore no longer appends the placeholder — `sendTurn` does, immediately after `settleSend`, so the mark clears as the placeholder arrives. Pre-ack the user row owns the indicator, post-ack the assistant row does, and the order never reverses. Two consequences. There is a sub-grace window with **no** indicator on a fast send, which is deliberate: the user's own bubble has just appeared, and the alternative (the placeholder appearing first and the mark then opening above it) is the row-to-row hop this replaced. And the append is **guarded on the room**, because it now runs after an await while `messages` is rebuilt per room — unguarded it would drop this turn's spinner into whichever transcript is on screen. The guard's failure mode is the one a room switch already produced: `updateMsg`/`enqueueStream` no-op against an absent cid, exactly as they did when the switch wiped the placeholder out from under a send in flight.

**Making a failed send durable** (chat-send-durability-fixes spec). ISSUE-200 made a failed send *visible* without making it *durable*: the `sendState: 'failed'` row was the only copy of the user's text, and three paths destroyed it — the room stream's own reconnect recovery, an ordinary page reload, and the composer dropping the draft the instant Send was pressed. A network outage triggers the first two at once, and it is the same outage that produced the failure, so the user watched their message be reported as unsent and then vanish. Four corrections, three of them client-side.

`messages` is a projection of server history — `loadHistory` and `loadViewPage` both `messages.set` a list built wholly from the response — and a failed send is the one row with no server copy, identifiable without ambiguity (`sendState === 'failed'` and no `msgId`, which every server row carries). Those rows are held in a room-keyed **`strandedSends`** map while off screen, put away by `stopActive` (the single "this transcript is about to be replaced" hook, which every clear path already calls) and taken back out by `carryClientOnlyRows` on the next rebuild, re-appended at the tail because that is where they were: a failed send is always the newest thing in its room from the client's point of view. Carried into **All**, which spans every room, and not into Unread or Starred, which are filtered panes a client-only row is not a member of — those leave the held rows alone, so the room's own transcript still gets them back. A deleted or hidden room drops its entry; the row was only ever going to be re-sent into that room.

**The draft is the second copy of an ordinary send, and is dropped on that send's ack rather than on submit.** (A *queued* message has a durable copy of its own from the moment it is accepted, so its draft goes on submit — see `queueing` above, which is also what decides between the two branches.) Nothing in the store survives a reload, so the stored draft is what restores the text into the composer when the row itself is gone — a downgrade from Retry to a re-send with no retyping, and the accepted outcome until ISSUE-202. The signal is **`sendSettled`** on the session — a counter *and the room it acked* — bumped by `settleSend` (which already runs at the moment the POST acks, ahead of everything downstream that can throw) and watched by the composer through a prop; the page translates the room into a draft key, because the composer owns the key's shape and passing a callback *into* it for it to call itself would be circular. `submit` writes the submitted text under the key rather than merely leaving it — a fast submit beats the debounce and would otherwise store nothing, or a stale prefix — and `flushDraft` holds it through the unsettled window, since every departure (a room switch, unmount, `pagehide`, `visibilitychange`) flushes an emptied field and would drop exactly the draft this exists to keep.

**Three constraints on that, each of which was a proven defect first.** The unsettled sends are a **map keyed by draft key**, not one slot, and the ack carries an identity: two sends can be open at once (leaving a room resets `status` to `'idle'`, which un-gates the composer), and with a bare counter the first ack dropped the second room's draft while its own POST was still open — destroying the only copy of it, which is the exact failure this whole section exists to prevent, reintroduced in a second place. `switchDraft` **refuses to restore a message still awaiting its ack**, even though it is stored under that key: putting it back in the field shows an already-sent message as unsent text, one Enter from being sent twice, and the ack then reads it as newly typed and declines to clear it, so it stays there for good. And the drop is withheld when something *has* been typed since — emptiness is a sufficient test for the on-screen room only because of the rule before it.

**`client_msg_id` moves retry identity to the server** — one nullable column on `messages`, a partial unique index on `(room_token, client_msg_id)`, and an empty string coerced to `NULL` on the way in, following `location_pings.client_id` (an empty string is a valid unique key and would collapse a room's whole history onto its first send). The client mints one per message (`crypto.randomUUID`, absent when the page is not a secure context, in which case the endpoint behaves exactly as it did before the field existed) and **reuses it on every retry**; `record_inbound` checks it after resolving the room and before creating anything, so a repeat resolves to the first turn and no second task, message row or Talk mirror exists (`_mirror_web_turn_as_user` reads the stamp it left as its own guard). The body-match adoption above stays as the fallback, because it is a heuristic that already fails on any send the server rewrites, and because rows predating the key have none. ISSUE-202's outbox needs the key regardless.

Three properties of that key are load-bearing and none is obvious. The lookup **returns the sender rather than filtering on it**: a room is shared and the key is arbitrary client-supplied text, so filtering would make a co-member's reused key miss and then collide on the room-scoped index, while ignoring the sender hands them a task `_authorize_task_access` will refuse them — instead the send **gives the key up** and proceeds without idempotency, which it is an optimization rather than a requirement. The endpoint **rejects an over-long key rather than truncating** it, since truncation changes the identity and two keys sharing a 64-char prefix would silently resolve to one another. And the replay deliberately **does not filter on task status**, though the spec's wording said non-terminal: a late replay would then find nothing, create a task, and take a `UNIQUE` violation on the insert. **A `!command` is the documented gap** — it runs inside the request and returns before the key is ever consulted, so a timed-out `!steer` or `!retry` cannot be re-POSTed safely; the client withholds Retry for any `!`-prefixed body rather than guessing which commands repeat cleanly.

Two pieces of per-room state were also not scoped to their room. An **upload in flight across a room switch** put its chip in the new room, and sending from there posted the file to the wrong one: `upload()` is async and appends with no notion of where it started, while `switchDraft` clears the list synchronously and cannot see a promise. A monotonic **`uploadEpoch`**, captured on entry and compared before each write, drops a stale result — including the counter decrement, since the switch has already reset it to 0 and a stale decrement would drive it negative and leave the composer reporting an upload forever. The file does reach the server and is orphaned there, the same outcome as closing the tab mid-upload. And the module-level **`pendingSend` echo buffer** survived a room switch that reset `status` to `'idle'`, defeating both gates the drain rested on (`send`'s `busy`, `retrySend`'s idle status): a second send then released the first's frames before its task id was stamped, showing two bubbles for one message. `runTurn` now holds its own buffer and drains only that one, and `stopActive` **abandons** the slot rather than draining it — those frames are for a room the user has left, whose transcript `loadHistory` rebuilds from the server on the way back in. The drain on the way *in* is a safety net rather than a step, and only because the third way into an overlapping same-room turn was closed with it: `Cmd/Ctrl+Enter` called `submit` without consulting the send/stop mode, so holding it started a second turn in a room that already had one. A key that sends is no longer refused mid-turn at all (ISSUE-238), so what keeps holding one down from reopening that hole is the store rather than the composer: `send()` branches on `status` before `runTurn` can be reached, and the second message is queued instead of starting a turn beside the first.

**A room's memory is readable and editable from the pane** (ISSUE-248). `CHANNEL.md` shapes every reply in the room and had no human-facing path: `!memory channel` dumped it into the transcript as a message, and the only writer was the memory skill CLI, whose `_channel_md_path` hard-requires `ISTOTA_CONVERSATION_TOKEN` and so runs only from inside a task. `GET`/`PUT /chat/rooms/{room_id}/memory` serve it under the existing room routes, behind a **Memory** entry in the room kebab, a sibling of Settings rather than a button inside it. `RoomMemory.svelte` mounts on the chat page next to `RoomSettings.svelte` and is keyed the same way (`{#if memoryRoom}`). Two reasons it is not a section in the settings pane: a full-text markdown editor does not fit 380px, and opening a modal from inside another modal is a shape nothing else in this frontend uses. The page reuses one instance across rooms — switching rooms while it is open swaps the props rather than remounting — which is why the component clears its buffer on load and gates its save on `loadedRoomId`. Editing the whole file is the honest shape: the section-level verbs the skill uses (`parse_sectioned_doc` / `apply_ops`) are an editing model for the agent, not for a person.

**Confinement is its own check, not a widened workspace root.** `_resolve_chat_file` is confined to `workspace_root(user_id)` with `is_admin=False` on purpose, and `/Channels/{token}` sits outside it by design, so `_chat_memory_room` carries its own rather than relaxing that one: `_chat_owned_room` resolves `room_id` → token, `storage.validate_conversation_token` runs before any path is built, and **`db.is_room_member` is then checked explicitly**. Owner scoping alone reads like a membership check and is not one — the handle is per-user (`ensure_web_chat_handle` gives every member of a shared Talk room their own), but it *outlives membership*: `_chat_delete_room` on a Talk-**backed** room deliberately keeps the handle row and merely archives it (the ISSUE-134 hide, widened past `origin` to any room with a live `talk` binding by ISSUE-408, so a promoted room is one), and `db.get_web_chat_room` applies no archived filter, so a user who left the room would have kept write access to the one file every remaining member's tasks are given as standing instructions. `db.delete_message` is the neighbouring room-wide write and gates on membership for exactly this reason. Unknown id, another user's handle, a non-member and an unsafe stored token all read as **404**, indistinguishable, so the endpoint is no id oracle.

**The save is optimistic, and the revision check is what the lock cannot cover.** `GET` returns an opaque `revision` which `PUT` must hand back; under `memory_md_lock` the file is re-read and a mismatch is a **409 `conflict`** rather than an overwrite. The lock alone is not enough, because its anchor dir is per-user (`deferred_lock_dir(config.temp_dir / user_id)`, matching `sleep_cycle` and the skill CLI) — a second member's task writing the same shared Talk-room file takes a *different* anchor and excludes nobody. Re-reading inside the lock rather than before it is the point: comparing outside leaves exactly the window the check exists to close.

**The revision hashes what a reader sees, not the bytes written.** `read_channel_memory` collapses absent and whitespace-only to `None`, so a file saved as `"  \n"` reads back as `""`; hashing the submitted bytes would hand the client a tag the next read can never reproduce, and every later save would 409 forever with no recovery but discarding the user's text.

**The busy refusal counts across every member.** `count_active_room_tasks` is the token-scoped sibling of `count_active_web_tasks`, added for this: delete is per-user because it drops only the caller's own handle, while `CHANNEL.md` is one object shared by the room, so a per-user count would refuse nothing in exactly the shared case that needs it. The client switches on `code`, so the two 409s take different recoveries: `conflict` keeps the typed text and offers a reload, `busy` says the room is working.

`storage.write_channel_memory` is the mount-side write — the executor reads this file into a prompt on every task in the room, so a reader must never see it half-written. **The staging name is unique per writer** (`tempfile.mkstemp`), and the skill CLI's `_atomic_write` was changed to match: both used to stage through a fixed `CHANNEL.md.tmp`, and since the lock anchor is per-user, two members of a shared room hold different locks and interleave into one staging file — publishing a mixture of both, which the revision check cannot catch because it guards a lost update and the tearing happens after it. `os.replace` was always atomic; the staging was not. Both sides pin UTF-8 explicitly, since the revision is a UTF-8 hash and a locale-dependent encode would make the same text hash two ways. The rclone branch is **not** atomic (`rclone rcat` streams the object) and its lock is a local courtesy keyed on a synthetic absolute path; the revision check is what makes a save safe on that shape. An `OSError` returns the documented `failed` status — a 500 carrying `code: "failed"` rather than an unstructured one — and unlinks the staging file. Body is capped at `_CHANNEL_MEMORY_MAX_BYTES` (256 KiB → **413**): the file is prompt text, so the bound is about what belongs in a system prompt rather than what the filesystem holds. `read_channel_memory` collapses absent and whitespace-only to `None` and the payload reports both as `exists: false`, so a cleared file reads back as the empty state; the pane then offers `CHANNEL_MEMORY_TEMPLATE`, served **from the server** so it cannot drift from what `init_channel_memory` writes. `USER.md` has the same gap and is deliberately untouched — whether it is one memory-editing surface with two scopes or two pieces of work is the decision that issue left open.

**Per-turn message actions** (ISSUE-210). One action row under each message body — copy, star, delete, left to right in ascending consequence — revealed on hover or on tap, keeping its layout box either way so revealing it never reflows the transcript. Copy takes `messageCopyText`: the turn's prose groups only, tool traces excluded, as **markdown source** rather than rendered HTML (which is why a fenced code block needs no copy button of its own). It is withheld mid-stream, because half an answer is not an answer; the star is not, because it marks the row rather than the text. **Delete is `DELETE /chat/messages/{message_id}` → `db.delete_message`** and it is _room-wide_, not per-user: the `messages` row is gone for every member, and authorization is membership (`db.is_room_member`), not authorship — the opposite of stars, which are per-user in `message_stars`. Unknown id and non-member both return **404**, deliberately indistinguishable so neither becomes an id oracle for the other (the same rule the star endpoint follows); a turn whose task is still in flight returns **409**, because the scheduler writes the assistant row at completion and the delete would silently undo itself. It is a hard delete, not a tombstone: every read path would have to learn to filter a tombstone, and the row would still occupy its slot in the `(room_token, role, task_id)` unique index, so re-running the turn would collide with a message the user believes they removed. It touches `messages` and `message_stars` only — never `task_events` or `tasks` (unlike a room delete) — and leaves `room_read_state` alone, since a read cursor is a high-water mark rather than a reference. **The `message_deletions` ledger exists because the room stream has a second cursor.** That stream tails `messages.id > cursor`, and a vanished row can carry nothing, so deletions get their own monotonic `message_deletions.id`; the `message_deleted` frame therefore carries no SSE `id:` (that cursor belongs to the message tail) and instead rides its cursor _inside_ the payload, which the client passes back as `since_deletion_id` on both `/chat/stream` and `/chat/events` — without it a reconnect after a delete silently resurrects the message. Like the message tail, the deletion cursor advances to the max id **scanned**, not the last one sent, or a client sitting behind someone else's invisible deletions never catches up and the O(1) gate stops short-circuiting. Rows are pruned after a fixed 30 days in `run_cleanup_checks` (`_MESSAGE_DELETION_RETENTION_DAYS`, deliberately not a config knob — the row is tiny and nothing about it is worth tuning). Propagation into a bound Talk room is best-effort and fire-and-forget, trying the user's own OAuth token first and the bot's second, because Talk lets only the author or a moderator delete and a mirrored user turn is authored by the _user_ while a reply is authored by the bot — so a 403 is the ordinary "not yours", not an error. A Talk failure never fails the web delete, which has already committed. Client-side the removal is **pessimistic**, unlike `toggleStar`: a row removed and then restored would reappear mid-transcript after the user watched it go.

**A `role='system'` row carries the same action row a turn does**, inside its content column and under its card. It was withheld for a while on the reading that a notice is not a turn — no author, nothing on the other side of it — but the server already supports every one of the four on a system row, and the argument was really about where the row sat: before the system branch took the gutter + content columns, the card began at the row's own edge and the action row under it lined up with nothing. Copy takes the markdown body a `!command` wrote, which is the whole reason a notice renders as markdown; `DELETE /chat/messages/{id}` has always accepted a system row's id; and a reply cites it through `db.get_reply_target`, which reads any `messages` row, with `_ensure_reply_parent_in_history` already naming a `role='system'` parent as one of the three cases that correctly fall through to the snapshot alone. Replying to an alert to ask what caused it is the ordinary thing to want. The one carve-out that stands on its own is **search results** (`!message.searchResults`): that row renders cards rather than markdown, so there is no source worth copying. The gating is otherwise the derived values unchanged, so a system row and a turn cannot disagree about what a durable id buys.

The row's **placement inside `.content`** is load-bearing rather than incidental — `.cmd-row` is a two-column flex row, so a third child would sit beside the card instead of under it. `.cmd-output` also shares one uniform `var(--space-2)` padding with `.external` and `DraftCard`, the other two filled blocks a content column holds: they stack under one another in the same column and their text has to start at one inset.

**Reply to a message.** A reply is an identified parent plus a rendered citation plus a prompt frame, and the three have to agree. The parent is addressed by canonical **`messages.id`** — the same id star and delete use — carried on the send as `reply_to_msg_id` and stored on two nullable columns: `tasks.reply_to_message_id` for the executor, and `messages.reply_to_message_id` so the transcript can still render the turn as a reply after retention deletes the task row. That duplication has its precedent in the same table (`messages.attachments` exists for the same reason), and there is deliberately **no foreign key** on the self-reference: keeping a dangling id is what lets a reply to a hard-deleted message say so instead of silently becoming an ordinary message.

**The namespace split is the whole reason this is a new column** rather than a reuse of `reply_to_talk_id`. That one resolves through `talk_message_id`/`talk_response_id`, and in a Talk-bound room — which is most of them, since web rooms promote and Talk rooms surface in web — canonical ids and Talk ids are both small integers in the *same* room. A canonical id stored there resolves to whichever Talk turn happens to share the number, the executor injects that turn as the message being replied to, and nothing at any layer notices. So `record_inbound` takes `reply_to_canonical_id` alongside the existing surface-native `reply_to_message_id`, and the parameter whose name matches the column is not the one that writes it — a collision worth stating so nobody helpfully merges them. `_ensure_reply_parent_in_history` resolves the canonical id first (through `db.get_reply_parent_task_by_message_id`) and falls back to the Talk lookup, so a task carrying both — a Talk reply whose canonical id was derived from it — takes the more precise of the two.

**The parent snapshot is derived server-side, never sent by the client.** The POST carries the id and nothing else; the server reads `messages.body` and caps it at the same 1000 characters Talk uses. A client-supplied quote would be text the model reads as an authoritative record of what it previously said, forgeable by anyone who can call the endpoint, and there is no reason to accept one for a row we hold. A parent in another room or an unknown id **refuses with 404**, indistinguishable, and creates no task — the same rule star and delete already set so no endpoint becomes an id oracle for another. Refusing rather than dropping the citation is the deliberate call: a reply body routinely depends on its referent ("yes, do that"), so a reply delivered without it is not the message the user wrote and produces a confidently wrong answer instead of a visible failure.

**Two prompt mechanisms, doing different jobs.** `build_prompt` renders the snapshot as a blockquote in the **request** section, unconditionally — the user's message is a response *to* that text, and `## Conversation context` is an ordered record where "this specific one" is not an entry. That frame replaced the old `(In reply to: …)` context fallbacks, which fired only when history came back empty and so vanished exactly when the marker was most needed; keeping both quoted the same 1000 characters twice. Separately, `_ensure_reply_parent_in_history` force-includes the parent's *whole* turn and marks it must-survive-triage, which is what saves a 5000-character parent from its own snapshot. Three cases fall through to the snapshot alone, all correctly: a `role='system'` row (no task), a turn retention deleted, and a turn that failed, was cancelled or is still running.

**Reading and rendering.** Every message dict gains an optional `reply_to` (`{msg_id, role, excerpt, deleted}`, or `{msg_id, deleted: true}`), emitted by all three producers — the per-room spine, the cross-room dict the aggregate panes and the live stream share, and the dev mock — because a reply that renders as a reply in one view and not another is worse than one that renders in neither. The parent is joined live (`LEFT JOIN messages p ON p.id = m.reply_to_message_id`, a primary-key lookup) rather than snapshotted, which is safe because nothing in the stack edits `messages.body`; a NULL join against a non-NULL id *is* the deleted case. The excerpt is capped at 200 characters — a **display** bound distinct from the prompt snapshot, and the composer's staged chip is capped at the same number so the chip and the reloaded quote cannot diverge for the life of a session. `buildHistoryMessage` is the single place the field becomes a row property, which is what keeps history, the aggregate panes and the stream in agreement.

**The refusal carve-out.** A 404 on a send that carried a citation classifies as its own `SendFailure` (`reply_target_gone`) — on the *intent* rather than on the error sentence, which is prose — and takes a recovery no other failure takes: the optimistic row is removed and the text and attachments go back to the composer. That contradicts the rule ISSUE-200 set, that a failed send never repopulates the box. The carve-out is narrow and earns itself: this is a synchronous pre-flight rejection of the citation rather than of the message, the offered Retry cannot work (it would re-POST the same dead parent), and no time has passed in which anything else could have been typed. Leaving a permanently un-retryable failed row is the strictly worse reading of the same rule.

**Talk in both directions.** A web reply into a Talk-bound room posts as a real Talk reply, using the parent's own Talk id out of the `external_ids` ledger (`db.get_message_external_id`, the value-returning sibling of the yes/no check); a parent that never reached Talk degrades to a plain post rather than being withheld. Inbound, `record_inbound` maps a Talk parent id back to a canonical id (`db.find_message_by_external_id`) and fills the canonical column too, so a Talk-origin reply renders as a reply in web. That lookup is **room-scoped** — a Talk message id is per-conversation — and it scans the room's stamped rows, since `external_ids` is a JSON blob; the same shape `message_has_external_id` and `room_max_talk_synced_message_id` already use, bounded by the room and run once per inbound reply.

**Client-side details worth keeping.** The Reply button is fourth in the turn action row (copy, star, reply, delete — ascending consequence, delete terminal), gated on a durable `msgId` like star and delete, and additionally withheld in the aggregate panes, which have no composer for a staged reply to go to. The touch overlays tile at the button *pitch* rather than at a flat 44px, so a fourth button needs no change to the formula. Escape clears the composer chip only **after** the autocomplete popover has declined it — the popover owns that key, and a chip taking it first would dismiss the citation while the user was closing a menu. A staged reply is part of the unsent message, so it rides in the draft as an optional `replyTo` (no storage migration: an absent optional field reads back absent), and an emptied field drops both — a citation is not itself a message. A `!command` clears the chip on send, since it returns from inside the request with no task for a citation to attach to. `MessageReply.deleted` is optional and truthy-tested: the composer stages without asserting a state only the server knows.

**A service worker serves the app shell, and it registers in the native shell alone** (ISSUE-202). Without one a cold launch with no connection never gets a document — the WebView is pointed at the deployment, so WebKit paints its own unreachable-server page and none of the offline machinery above ever runs, which is the whole of what `src/service-worker.ts` exists to fix. Kit's automatic registration is turned **off** (`kit.serviceWorker.register: false`) and `routes/+layout.svelte` registers it behind `shellAtLeast('0.10.0')` — the shell alone would do for blast radius (this app deploys continuously and a worker is the one client artifact that can pin a client to a build the server has deleted), but the version is what the facade's own rule asks for and it is what pairs the worker with the settings row that can remove one, so an older app cannot install something it has no way out of. Install precaches `build` plus an allowlist from `files` all-or-nothing, then adds each `prerendered` document tolerantly — forty documents where one deployment quirk must cost that route's offline boot rather than the feature. Activate deletes the other `istota-` generations and claims; there is no `skipWaiting`, so a new build activates on the next launch, which is what the update prompt already tells the user to do. The worker needs `WKAppBoundDomains` **and** Capacitor's `limitsNavigationsToAppBoundDomains` on the shell side, which is undocumented WebKit behaviour Apple DTS calls unsupported: if it ever goes away, cold-launch offline stops working and nothing else does.

**The routing table is the safety story, and two rows of it are the whole of it.** Nothing under `${base}/api/` is ever cached — data caching is the app's job, in IndexedDB, keyed by user and bounded per room and read by code that knows what a stale message means, where a `Cache` of authenticated JSON would be a second dumber cache that survives a logout and answers a 401-worthy request with the last session's data. And an `Accept: text/event-stream` request passes through untouched whatever its path, because an SSE response never ends and reading its body to clone it stalls the stream. Beyond those: `_app/immutable/` cache-first (content-hashed, so a hit is correct by construction), a navigation network-first, anything else precached cache-first, everything else network with a 503 on failure — which is where `version.json` lands, deliberately, or the stale-build prompt stops firing. `routeFor` is exported and pure precisely so that table is a test rather than a comment. **The navigation fallback tries more than one spelling of the path, and stops there**: Kit names a prerendered document with a trailing slash and every link in the app points at the route without one, so matching the request's own path alone misses every document in the cache — while falling through to the app root for *any* path would answer the server-rendered routes the app navigates out to (`login`, `logout`, `reconnect`, the OAuth starts) with a 200 carrying the app shell. Which is also why the 3s timeout runs only where there is a cached document to fall back to: a route this build does not carry is the network's alone, and cutting it off would fail a slow sign-in that was about to succeed. The cached document is copied into a fresh `Response` carrying its content type and nothing else — a response fetched through a redirect is marked as such, and answering a navigation with one throws in the page.

**A cold launch reads the cache by a pointer, and the pointer is read only in the shell.** Every cache key is namespaced by `cfg.user_id`, which arrives on `GET /chat/config` — a fetch a cold launch offline never gets, so without a stand-in it boots to an empty cache, which is the one outcome this stage exists to prevent. `offline/lastUser.ts` holds `chat.lastUserId`, written by `init()` on every successful config read and read back as the seed only when `isNativeShell()`. That gate is what makes it safe rather than a hole in the namespacing it undoes: the namespace guards a shared browser profile, and the shell is one device, one session cookie, one person — and the only surface with a worker to cold-launch offline at all. `forgetLastUserId` runs wherever a session ends — the root layout's 401 path, the money layout's, and `LogoutButton`, which is the likelier one on a device that changes hands. **A guess decides what is painted and nothing else.** While it stands, `cacheUserId()` is null so no cache write can land in the guessed namespace — the ordinary "launched in a lift, signal returned" sequence would otherwise write the real session's rooms and transcripts under the guessed id, which is the cross-user read the namespace prevents, arrived at from the writing side — and `canDrain` refuses, so nothing is POSTed under an identity the server has not confirmed. Underneath that is `settleSeededUser`, which the first config that answers runs (in `init`, and once from `onBackOnline` for a session that booted from the guess). A confirmed guess costs nothing. A wrong one drops the transcript, the room list and the selected room (a room id out of another namespace is a rowid that means something else here), and splits the queue: entries the restore read out of the guessed id's storage are that person's and are left in storage for their own next session, while entries *this* session typed were keyed by the guess and are taken back out of it, or they would be restored and auto-sent as the guessed user later. `restoredCids` is what tells the two apart.

**The identity is cached too, because the root layout gates the app on it** (ISSUE-354). Everything above renders under `{@render children()}`, and `routes/+layout.svelte` renders that only once `getMe()` has answered — so with no connection the whole feature failed one layer above itself, at `error = 'Failed to load user info'`, with the cached rooms, the cached transcripts, the banner and the queue all present, correct and unreachable. `readUser` / `writeUser` in `offline/db.ts` hold the `User` under a second key shape in the existing `config` store (`<user>:me`), not a fifth object store: `DB_VERSION` is 1, all four stores were created at once so no later stage needs a bump, and a bump is the one IndexedDB operation another open tab can block. Two key shapes in one store can be spelled by each other — a user named `alice:me` keys its config where `alice`'s identity goes — and the guard is the **shape check**, not the key: each reader refuses a record of the other's shape, so a collision degrades to a null and never to a cross-user identity read. `readUser` validates to the depth the nav dereferences (`username`, and `features` as an object) for the same reason `readRow` does: a record without `features` throws inside the template rather than in the caller, and the layout then renders none of its three branches, which is worse than the error page this replaces. The read is keyed by `seedUserId()`, and `canReadCachedUser()` — the one spelling of the shell gate — is what `writeUser`'s caller checks too, so the record exists only where it can be read and where "Clear offline data" can remove it. The pointer beside it stays ungated: one string, nothing personal, and the shell wants to find one already there. The record the layout resolves — cached or live — is published to every route through `lib/userContext.ts` rather than each of them fetching `/me` again (ISSUE-355); `web/AGENTS.md` carries that rule, and the chat page's author labels and draft key read it from there.

The `catch` now makes three answers where it made one, and keeping them apart is the whole of it. `AuthError` still forgets the pointer and redirects, ahead of every offline branch and ahead of the generation check too — a dead session and a dead network are different answers, and a 401 is authoritative whoever asked. A failure the connectivity store says was a *gap* falls back to the cached identity; the store is read rather than the exception being classified a second time, the same read `init()` makes when its room list fetch fails, so a 500 stays a server that answered and still reaches the error. Everything else, first launch included, is still the error page. The fallback path deliberately starts no notification poll and writes nothing back — the poll would back off against the connection that just failed, and re-storing what the cache just answered with would push its own expiry out forever and make the pointer self-confirming. Both happen on the retry instead.

**The retry is what makes the fallback safe, and three details in it are load-bearing.** It waits on `live` — did the *server* answer this session — rather than on "booted from the cache", so the error page retries too; that page is otherwise the one screen with no way out, since the shell has no reload affordance. It listens on both `online` and `visibilitychange`, because a retry that fails against a server that answered leaves the store online and no further connectivity edge is coming, and the user returning to the app is the signal the probe and the notification poll already use for exactly that. And `loadUser` carries the generation counter `chat.ts` and `notifications.ts` both carry: a reconnect can start a second load while the first is still awaiting, and without it the slower one wins whatever it has — a month-old cached identity painted over the live one. `getMe()` is bounded (`ME_TIMEOUT_MS`) for the other half of that: unbounded, a stalled request outlives the store's own 5s probe, and the classification then reads "online" for a request that plainly was not.

`getMe()` is also a second writer of `chat.lastUserId`, alongside `init()`'s config read. The values agree by construction — `cfg.user_id` *is* the username, both from `user["username"]` on the same session — and the layout runs on every route, so a session that never opens chat still leaves the shell able to find what it stored. It cannot confirm a wrong guess: `settleSeededUser` compares the live config against the id `init()` captured in its own closure, not against a re-read of the pointer.

**"Clear offline data" is the escape hatch, and it is a settings row rather than a debug affordance.** `offline/clear.ts` unregisters the workers scoped under this app's base path (not the origin's — the deployment may carry a neighbour's), deletes this app's `istota-` caches and calls `clearOffline()` (which empties all four object stores in one transaction, for every user on the profile — someone asking for the offline data to be cleared is not asking for another account's to be kept), and the page then reloads so the next document comes from the network. The first two steps are best-effort and counted; the database step is the one place in `offline/db.ts` that **reports** rather than swallowing, because the caller reloads on success and reloading over a clear that did nothing presents the failure as the fix. It is gated on `shellAtLeast('0.10.0')` — the shell version that declares the app-bound domains — since off the shell there is no worker and the reload the user already knows is the whole remedy. The row sits outside the settings page's `{#if profile}` block deliberately: the profile fetch is the first thing that fails when the server is unreachable, and a row that disappears exactly when it is needed is not an escape hatch. The send queue is untouched by it; the held blobs are not, and that is what the confirmation says.

**App shell and caching.** Static responses carry two cache classes — hashed `_app/immutable/` assets immutable for a year, everything else (the HTML shell, `version.json`, the manifest, icons) `no-cache` and revalidating. Sending neither let an installed home-screen app pin the shell indefinitely and then request hashed chunks the server had deleted. A new build is surfaced rather than forced: SvelteKit's version poll drives a toast with a Reload button (a tap, because a reload discards a half-typed message), re-checked on `visibilitychange` since the poll timer is throttled in a background tab and stopped in a suspended PWA. The web unit passes `--timeout-graceful-shutdown` for a related reason — `GET /chat/stream` is session-lived and exits only on client disconnect, which server shutdown does not trigger, so a restart with any browser tab open used to sit out the full stop timeout and die on SIGKILL. Docker's web service has no equivalent flag. That deadline is a backstop now: all three SSE generators observe `istota.web_shutdown`, which wraps the process's SIGINT/SIGTERM from the app's lifespan, and return when it fires — so a restart drains immediately instead of running the window out and having the ASGI task cancelled, which uvicorn logs as `Exception in ASGI application` with a `CancelledError` traceback.

Knobs under `[web.chat]`. Frontend engine in `web/src/lib/stores/chat.ts` (SSE with polling fallback) + widgets in `web/src/lib/components/chat/`. **Body render model**: an assistant turn is an ordered list of `text`/`tool`/`thinking`/`notice` segments (`segments.ts`) — `notice` is an out-of-band statement about the *run* rather than its content (today only a `brain_fallback`, ISSUE-278), rendered as its own warn-tinted `.banner warn` group in true segment order, never coalesced into a chip, and excluded from `messageCopyText` alongside the tool trace. It is deliberately not counted as content by the streaming cue in `Message.svelte`: a notice is a static sentence and the fallback run after it is the long part of the wait, so the pulsing dot and ack verb stay up under a turn whose only groups are notices. It is also **live-only** — the `task_events` row survives pruning and an SSE resume, but `_trace_segments` / `historySegments` rebuild a finished turn from `execution_trace`, which carries no notice, so a reload shows the answer without it; `renderGroups` reduces it to interleaved render groups — substantial prose blocks (trimmed length ≥ `SUBSTANTIAL_TEXT_CHARS`, mirrors the backend gate) render as prominent markdown in true order, consecutive tools coalesce into one `ActivityTrace` chip, short lead-in narration + reasoning are dropped, and the trailing text is always the answer. This keeps a meaty intermediate block (analysis the model wrote, then acted on) visible as its own prose block instead of vanishing when the next tool settles it — the live stream and a reloaded-from-`execution_trace` turn build the same groups. Not a Talk replacement — an in-app companion. Web chat is also a _delivery_ surface (ISSUE-121): alerts, the verbose execution log, and notifications routed to `web` are appended to a room as unsolicited system messages (distinct from task-backed turns, written into the canonical `messages` store as `role='system'` rows) and merged into room history by time. See `WebTransport` in the Transport abstraction section. **Unread indicators**: the sidebar bolds a room name and shows a count chip for rooms with unseen messages. Counts are server-computed in the `/chat/rooms` payload (`db.count_unread_messages` — `messages` past the per-user/per-surface `room_read_state` cursor, excluding `role='user'` so your own/Talk-mirrored turns don't ring your own room); `db.initialize_room_read_state` seeds a freshly-surfaced room's cursor to its current max so a backlog doesn't read as unread. Opening a room (or `POST /chat/rooms/{id}/read` → `_chat_mark_room_read`) advances the cursor to the room's newest message; the client persists on open / stream-append / stream-settle / `visibilitychange` (visibility-gated). The active room is held at 0.

**Pending confirmations are an inbox item, not a card in a room** (ISSUE-241, then the notification-inbox spec). The in-room `ConfirmationCard` covers a turn the user started here; it cannot cover the one they did not. An inbound email held by the untrusted-sender gate has its transcript mirror deliberately withheld (`suppress_transcript_mirror`) until the answer, so there is no row to hang a card on. That withheld row is also what keeps it out of the room history query: `_AUX_ROOM_SCOPE` admits an email task only through a mirrored `role='user'` row, and admitting a held one would publish `tasks.prompt`, which for a gated email is exactly the untrusted body the gate exists to hold back. (Since ISSUE-247 the exchange *does* have a room — resolved from the routing — so the withheld mirror is the whole of the argument; the old "its token belongs to no room" half no longer holds.)

**That question now lives in the notification bell, not in a strip above the transcript.** `GET /chat/confirmations`, its `_chat_pending_confirmations` builder and `PendingConfirmations.svelte` are gone, along with the `pendingConfirmations` / `refreshConfirmations` / `answerConfirmation` slice of the chat store. The `confirmation` source in `notification_store` carries the same question — the same `confirmations.describe` label, the same attacker-supplied text rendered into a text node, the same `/chat/tasks/{id}/confirm` and `/cancel` behind Confirm and Discard — and carries it from *every* route rather than only from `/chat`, which is what the strip could never do. The chat page keeps the fast path: the room stream's `notifications` frame sets the bell's count in about a second where the root layout's 30-second poll is the contract. `!confirm <task-id>` still works from the composer on any surface.

**A room-surface confirmation now appears in both places at once, and that is the intended trade.** The banner excluded a gate whose own turn already drew a `ConfirmationCard`, because two answer paths in one pane leave the card stale when the other is used. The bell is not in that pane: it is a global list of what is waiting, and a room-surface gate waiting in it is the same claim the card makes in the transcript. `scheduler.py`'s park writes the row for every confirmation whatever else carries it — only *delivery* is suppressed where the room leg already asked — so the resolver applies no `source_type` filter either. Answering from either surface closes the task and the row. **One rough edge is known and unfixed:** `m.confirmation = false` is set only by the chat store's own `confirm` / `reject`, so answering the *same* question from the bell leaves the in-transcript card on screen until the room stream's next frame or a reload — the POST goes straight to `/chat/tasks/{id}/confirm` and the chat session never hears about it. Pressing the stale card afterwards is harmless (`_chat_confirm_task` no-ops unless the task is still `pending_confirmation`), but it reads as the answer not having taken. Fixing it means one store telling the other what was answered, which is the coupling both sides currently refuse; nobody has designed that yet. **The composer is a second producer of the same rough edge**, and ISSUE-350 widened it: `applyInlineResult`'s `confirmation_answered` branch stamps `msg_id` on two rows and does not clear `m.confirmation`, reset the row, or `enqueueStream` the way `confirm()` does — so answering with `!confirm`, or now with `!yes` / `!no` / `!y` / `!n` / `!approve` / `!decline` / `!reject`, leaves the card up the same way the bell does. It is not a regression: the spellings already took this path from an idle room, which is what a room parked on a confirmation is. What changed is that they now also fire from a *busy* room (a second task streaming while an earlier one is parked), where previously they were queued and a parked turn holds the queue, so the answer never fired at all. The resume half is unverified — whether `pickUpStreamedTask` re-adopts a task resumed this way off the room stream needs a live `full`-profile run, since the client never enqueued it.

**Two chat-pane strips came out and two in-transcript cards stayed.** The floating strips were `PendingConfirmations.svelte` and the `looseDrafts` list of banner-placement `DraftCard`s; both were pane chrome competing with the transcript for the top of the pane, and both are the inbox's job now. `ConfirmationCard.svelte` and the inline `DraftCard` under the assistant row whose task composed the draft belong to a turn the user started in that room, in sequence, and are untouched — as are `GET /chat/drafts`, the whole draft store slice, the `drafts` SSE frame and the `draftsByTask` map that places the inline card.

**Being offline is a sticky notice, not a banner.** It has had three homes and the second was the instructive one. It began as a row inside the composer dock, where it read as a caption on the text box and forced the dock to render in the composer-less aggregate panes just to carry it. It then became a `NoticeBanner` in `AppShell`'s `extras` band — which fixed the reading and cost layout instead: a bordered card with a bold title, about 55px of a phone's pane for one sentence of chrome, pushing the transcript down by roughly a fifth of the visible messages. The band `NoticeDrawer` owns is absolutely positioned, so it overlays; the transcript measured 610.62px in a browser both online and off. That measurement is the whole argument, and it is the one thing the suite cannot check — jsdom performs no layout, so a height assertion there passes with a 55px band deliberately reintroduced. `offlineBanner.svelte.test.ts` asserts structurally instead (every node carrying the sentence belongs to the drawer) and `AppShell.notices.svelte.test.ts` pins `position: absolute` against the drawer's source.

**`sticky` is what makes a notice honest for a condition** (`notices.ts`). The store is built for events, and three of its mechanisms would each retract a live condition: `clearNotices()` on navigation, the `PINNED_HANDOVER_MS` handover once anything queues behind it, and the `MAX_QUEUE` trim. A sticky notice is exempt from all three — the earlier reading that a `duration: 0` notice would do was wrong on each of them. What it is deliberately *not* exempt from is holding the slot, since silencing the channel for the length of an outage is the hazard the handover exists to prevent: a sticky head yields to any event immediately and takes the slot back when the queue drains to it. `notices.sticky.test.ts` owns those semantics, with a control that neuters the flag and turns five of nine red.

The page owns the lifecycle: an effect on `$online` raises and dismisses it, and `onDestroy` takes it down, because sticky survives the navigation clear and the sentence promises the send queue will drain — which no other route has to promise. That is also why it stays chat-scoped rather than moving into `AppShell`; an app-wide offline notice needs wording that is true on the map and the money pages, which is a separate decision.

**A held outbound draft is a card under its own turn.** `DraftCard.svelte` renders one held email — the recipients, the subject and the **whole** drafted body, as a text node under `white-space: pre-wrap`, never markdown. That is the single promise the feature makes: approving sends exactly the bytes that were read, so a card that abbreviated or re-rendered would break it. It goes **inline under the assistant row** whose task composed it, which is where the drafted text and the "this task also created a calendar event" summary read together — keyed on the assistant row alone, since a turn's user and assistant rows share one task id and keying on the id would draw every card twice. Everything else — a task with no room (a cron job mailing an external address), a turn paged out of view, a turn whose task row retention deleted — is in the notification bell. It used to fall to a strip above the transcript, and the invariant that strip carried still holds: no draft can be hidden by failing to find a home in the transcript. The actions summary is **read-only**: reversing a calendar write needs a per-task ledger of reversible operations, which `actions_taken` (rendered strings, not structured ops) cannot back and which is its own feature.

Three states the card must be able to show, and none of them existed in the Stage 5 payload. A row stuck in **`sending`** — the process died between the claim and the finalize — was filtered out by every `status='pending'` producer, so the one state that needs "check your Sent folder" was the one state invisible on the whole web surface; `outbound_drafts.open_for_user` carries `pending` and `sending` both, and the card offers *no* action on it, since nobody can know whether the mail went out and one of the actions would send it twice. A row whose stored JSON does not parse is reported as an **id in `DraftListing.unreadable`** rather than raising: strictness is right inside `release` (sending to a recipient set we cannot read is exactly the thing to refuse) and wrong in a listing, where one bad row 500'd `GET /chat/drafts` and emptied the stream frame for the other nine. It is named rather than dropped, because held mail that silently disappears is mail the user never hears about — and it stays discardable, which is why ownership checks and `discard` now read through `outbound_drafts.identity` (the two plain columns, parsing nothing). Approving one still refuses. And the drafts frame is **byte-budgeted** (`_DRAFT_FRAME_MAX_BYTES`), unlike the message tail's per-row cost: a body is capped only by the 200k PATCH ceiling, the whole set rides *every* frame, and every open connection pays — so past the budget a draft rides as a stub carrying id, room and status, and the card fetches the full row from `GET /chat/drafts`, which is deliberately not budgeted. The first draft always rides whole, or the budget could make the frame useless exactly when it matters.

Client-side, **a 409 is read against the action, never on its own** — the same status means opposite things to Send and to Discard, and getting that wrong is how a refusal comes to look like a success. "Already discarded elsewhere" *settles* a discard (the card goes, silently, since that is what was asked for) and *refuses* a send (the card goes, but with a notice saying nothing was sent — dropping it quietly would give the user who pressed Send exactly the feedback a successful send gives). `sending` keeps the card on either action and says the mail is in motion. `sent_unrecorded` never offers a retry. Two supporting rules make that readable: **every route that can 409 carries `state`** — the discard route did not at first, and the client's default of `gone` turned "we don't know" into the drop-it-silently branch — and a missing `state` now stays `undefined` and keeps the card, so a future route that forgets fails safe.

**The optimistic removal is held down only where the server accepted the answer.** `_drafts_snapshot` runs on a worker thread on the room-check tick, so a read taken a moment before `release` committed its claim arrives *after* the answer and puts the card back with a live Send button on mail already going out. A short window (`ANSWERED_SUPPRESS_MS`) filters those ids out of an incoming snapshot. It is deliberately **not** applied on a refusal: there the row may still be held, and suppressing would hide answerable mail for the window's whole length — so those paths drop the card and let the re-read be the authority, which puts it back if it is still there.

The set is **seeded on entry** for a reason the confirmations banner does not have: the frame is a *diff* against a baseline seeded `[]`, so an instance whose set has not changed since the connection opened pushes no frame at all. `recoverStream` refreshes it too, metadata-only recoveries included — a backgrounded tab is exactly where an approval given on the phone would otherwise leave a card up for a message already sent. `refreshDrafts` **coalesces concurrent callers onto one request**, because a frame that stubs K drafts makes K cards each ask for the full row against an endpoint that is deliberately un-budgeted; without it the frame's byte budget is "saved" by fetching every body K times.

**The two placements are a prop, not two components** (`placement: 'turn' | 'banner'`), and `banner` is a different **shape** rather than a shorter one. The reader arrived at the inline card by scrolling to it and the body is what they came for, so `turn` is the full card: the fields grid, the body at a 700-character preview, the actions list. `banner` was chrome nobody asked for, pinned above the transcript beside the confirmations strip and competing with the transcript for the top of the pane, so `compact` is four rows — the head, recipients and subject folded onto one line, one clipped line of body, and the buttons — expanding to the full card in place and back.

**Shortening the preview was tried first and was not enough**, which is the part worth keeping. At 180 characters a body carrying a blank line still rendered as two paragraphs, because the block is `white-space: pre-wrap` and honours the break; the fields grid still spent a row each on To and Subject; and the actions list and button row were rows of their own. Two held drafts still took most of the pane (360px, scrolling, with the buttons clipped below the fold). The compact card is 145px. So the peek **collapses whitespace** (`body.replace(/\s+/g, ' ')`) — it is a label for the held message, not the message — and clips in **CSS** rather than at a character count, since the card's width varies with the pane and a count that fits at one width is wrong at another. That is also what kept a stack of drafts off the strip's `max-height: 40vh`, which otherwise turned the list into a scroller at the top of the pane.

Compact hides **detail, not decisions**: Send, Edit and Discard are all on the compact card, because answering without opening anything is the point of it. `editing` is excluded from `compact` — the textarea is the full-height writing surface the card exists to offer, and there is no compact way to write a reply — and the `unreadable` / `truncated` / `sending` branches are checked ahead of it, since none carries a body to peek at and a stuck row's card is a "check your Sent folder" notice rather than a decision. Truncating is a **reading** decision and never an abbreviation of what is sent: `Send` and `Edit` both operate on the full stored `body`, never on `shownBody` or `peek`, and the body is a text node that is never re-rendered — so the feature's promise is about transformation, not about how much is on screen at once. The component's docstring used to say a card that abbreviated would break the promise, which its own `PREVIEW_CHARS` had already contradicted.

**The `--chat-body-max` cap travels with the slot, not the card.** Inline the card is one block in a turn's content column and has to stop where the prose body above it stops, so the cap is written in `Message.svelte` on `.content > :global(.draft-card)` — beside the top spacing, which is scoped there for exactly the same reason. On the component it also applied in `banner` placement, which is pane chrome spanning its container: in the chat pane's own strip the draft stopped **134px** short of the confirmation card directly above it (900px against a 1034px card in a 1060px pane), at the one width the two most obviously wanted to agree on. Both strips are gone, but the reasoning is what decides where the rule lives and `banner` is still a placement the component takes. Pinned in `DraftCard.svelte.test.ts` against the **source**, not a computed style: jsdom does not apply a Svelte component's own `<style>`, so `getComputedStyle(card).maxWidth` reads `none` whether the rule is there or not — vacuous in the one direction that matters. Note also that the existing "no margin on `.draft-card`" assertion regexes the raw file, comments included, so prose inside that rule must avoid the word.

Two things about the stub path that were defects first. The card's "I need the full row" latch **resets when the row stops being truncated** rather than being once-per-instance: the frame is diffed against the server's own baseline, which the client's refetch does not touch, so the same draft is stubbed again on the next frame that changes anything — and a permanent latch left the card on "Loading…" forever with no way to answer the mail. And `_draft_stub` carries **`task_id`**, the field that actually places the card; without it a stub moved its own card out of its turn into the fallback list and back as the full row landed, which destroys and recreates the component and throws away a correction being typed.

**A turn that arrived from outside the room says so, and the reader decides how much of it to read.** The inbound mirror writes an external contact's mail as a canonical `role='user'` row, and `origin_surface` — which has always been on the row — was dropped on the way out: a stranger's message rendered as an ordinary user bubble with an unfamiliar name in it, full body, no provenance, no collapse. Both SQL fragments now select it (`db._CROSS_ROOM_COLUMNS` and `web_app._SPINE_COLUMNS`, deliberately both, since they exist as shared pieces precisely so the room tail and the history query cannot disagree), and `_user_row_display` — the one builder both producers go through — publishes `origin`. `subject` rides along from the same place, because the wrapper the display body strips is where it lives and a collapsed turn shows it in place of the body; a prompt that parses to an **empty** body publishes an empty `text` rather than the wrapper, or an attachment-only mail previews as `<email_metadata>` and expands to an instruction addressed to the model. The subject is capped (`_SUBJECT_MAX_CHARS`) for the reason the reply excerpt is truncated in SQL: it is an attacker-supplied header of no fixed length, and this dict rides the byte-budgeted room-event stream.

**`author_id` rides beside `author`, on that branch alone.** The label is a display string and the avatar endpoint keys on a user id, so a co-member's turn could be named but not pictured. The id is emitted under exactly the condition the label's own `elif` states — a user id, not the viewer's, and no `author_label` — so an external sender still carries a name and no id, and the client asks for no picture for an address with no account behind it. The viewer's own row carries neither, which is what tells the client to draw its own face from the hash `/me` gave it. What deliberately does not travel is that hash for anybody else (D13 of the profile-icons spec): one field per row against one conditional request per author per session, on a stream that is already byte-budgeted.

**`origin` needs two conditions and the second is the one that is easy to miss.** The surface must be one the room does not itself live on — `not surfaces.is_room_member(origin_surface)`, which is talk and web — *and* the row must carry an `author_label`. Surface alone was the first cut and it was wrong in the mirror image of the case it was protecting: a user mailing their own plus-address writes an `origin_surface='email'` row that is nonetheless their own words, so the reader got the stranger's treatment applied to themselves — "External email" over their own message, collapsed. `transport.ingest.resolve_author` already draws exactly this line, setting `author_label` **iff** the envelope sender is not one of the user's own addresses, and it is safe to gate on because it is never absent for a genuine outsider: an unclassifiable sender falls back to `UNATTRIBUTED_SENDER` rather than to nothing. Absence of `origin` therefore means "from inside this conversation" for a colleague's Talk turn and for your own forwarded mail alike. Client-side the *label* is derived rather than hardcoded (`External email` / `External message`): the server's contract is the ownership predicate read negated, which resolves to email today only because `TRANSCRIPT_SURFACE_FILTER` limits user rows to web/talk/email, and nothing enforces that coupling across the two files. It is also the one site where an unrecognised surface name is the *unsafe* answer: everywhere else the leaf's "not a room surface" default fails closed, and here it renders a genuine Talk turn as external. See "The room model" in `.claude/rules/transport.md`.

**The wrapper the display body strips has to be the wrapper the poller wrote (ISSUE-274).** `email_support.parse_email_prompt` is what turns a stored email turn into something a human reads, and returning `None` means "render verbatim" at its one call site. It anchored the closing tags at column 0; the builder in `transport/email/inbound.py` is an f-string nested eight levels deep, so it emitted `\n        </email_metadata>`. The parser therefore matched nothing on every real prompt it was ever handed, and the transcript showed the user the wrapper tags, the untrusted-input guard and the trailing instruction addressed to the model — in a bubble labelled with their own name, which is the exact mislabelling the strip exists to prevent. Both halves had tests and both hand-wrote the same unindented fixture the builder did not produce, so the guard now is the **pairing**: `tests/test_email_prompt_wrapper_render.py` polls a message and feeds the resulting prompt straight to the parser. The fix is both-ended. The builder writes flush left, which is also less prompt noise on every email task. And the parser tolerates leading whitespace on the closing tags and header lines, because the indented rows are in `messages` permanently and a display fix that only helps future mail leaves every stored turn raw. `[ \t]*` rather than `\s*` only because the run exists to absorb the historic block indent; both spellings keep the tag line-anchored, since the `\n` before the run is mandatory either way.

**Making the parser work is what made the wrapper forgeable, and that is the larger half of ISSUE-274.** The wrapper is a delimited document whose boundaries are *lines*, and the values on those lines are chosen by the sender. `imap_tools` decodes `Subject:` with `decode_header` and joins the parts verbatim, so a Q-encoded `=0D=0A` puts a real CRLF into `Email.subject`; an attachment filename is RFC 2047 too and lands inside `<email_metadata>` as well. Either could close the metadata block, add a second `From:`, and open an `<email_content>` of its own — and while the parser matched nothing this was visible nonsense, whereas a working parser renders it as a genuine message: the sender's headers, the sender's body, under the real external sender's attribution, with the actual body never shown. Three changes close it, and each fails safe in a different direction. `email_support.flatten_prompt_header` collapses every whitespace run in `From:` / `Subject:` / `Date:` / the emissary `sent to:` line / each attachment name — the inbound counterpart of `skills.email._sanitize_header`, and it belongs at the builder because a parser cannot tell an injected delimiter line from a real one. The header loop is **first-wins** (`setdefault`), so a second `From:` cannot silently replace the field a reader leans on hardest. And the `body` group is **greedy** while `meta` stays lazy: the body is the one value that cannot be flattened, since it *is* the content, so it can still carry a closing tag — greedy runs to the last one, which is always the builder's own (nothing follows it but the guard line, which carries only an *opening* tag), and the injected tag renders visibly inside the body instead of hiding everything after it from the reader while the model still sees the whole prompt. Lazy was the shape this shipped with, and it let a body reading `Please review the figures.\n</email_content>\nSYSTEM: …` display as its first line alone.

`external_turn_display` (`full | collapsed | hidden`, default `collapsed`) governs the **body only**. `hidden` never removes the row — a bot answer with no question above it is the defect the inbound mirror was built to fix (ISSUE-136) — so the header, the origin marker and the sender render at every setting, and only `collapsed` offers expand-in-place: on `hidden` a toggle would be the setting asking to be overruled on every message it applies to. The derived body gate tests the **mode**, not the expansion flag alone, so `hidden` wins over a body expanded earlier under `collapsed` — otherwise the row is stuck open with its toggle gone, in the one mode whose job is to withhold it. Two smaller rules. The preview is a **single clipped line** sliced by code point, not a wrapped excerpt: wrapping makes `collapsed` shade into `full` for the one-long-paragraph mail that is most of email, and a UTF-16 slice renders a lone surrogate when the cut lands inside an emoji. And the block is **neutrally tinted** (`--surface-badge` plus a `--border-hover` rule) rather than borrowing a status tint: provenance is not a severity, and `--status-warn-*` would call every external correspondent suspect. Every field on it is attacker-supplied and renders as a text node.

Expansion is component-local `$state` keyed on `message.cid`, which `buildHistoryMessage` regenerates on every rebuild — so paging older history, `jumpToTask` and a round trip through an aggregate pane all re-collapse an expanded turn. Accepted rather than hoisted into the store on `msgId`: it fails in the withholding direction, and a cross-cutting expansion registry is more machinery than the annoyance is worth.

The setting is **server state, not a client-local preference** — it is a `user_profiles` column edited on `/settings`, published by both `GET /chat/config` (which the chat store reads at `init`) and `GET /settings/profile` (which the pane edits) — because how much of a stranger's mail a reader wants inline is a decision about the account, not about the browser they happen to be on. It is the counter-example to theme and text scale, which are localStorage for the pre-paint reason. **`/chat/config` reads it live from `user_profiles`, not off the `_config.users` snapshot** the rest of that handler uses: the snapshot is rebuilt only by `_reload_config` (startup and SIGHUP) while `PUT /settings/profile` deliberately syncs nothing in memory, so resolving it there had the pane show the new value from its own live read while the transcript kept applying the old one until a restart. `outbound_approval` on the same handler still has that staleness; nothing edits it yet, and closing it means moving `effective_policy` off the snapshot too. The PUT **rejects an unrecognized value** rather than folding it onto the default, since a stored string the code ignores would leave the pane rendering a selection nobody made; the client normalizes anyway (`stores/externalTurns.ts`) for the hand-edited row the route never saw. That normalizer sits beside the store rather than on `$lib/api` for a reason worth not rediscovering: eleven store test files `vi.mock('$lib/api', …)` wholesale, so a *function* exported from there is `undefined` in every one of them — the type is erased and can stay.

**A bare "yes" answers from the composer too, and the exchange is durable** (ISSUE-243). The Talk poller had intercepted a confirmation reply before task creation since it was written; web had no equivalent, so "yes" fell through to `_chat_create_web_task` — which room-scoped-cancels pending confirmations on a new message, so a same-room gate was **cancelled by its own approval**, and a cross-room email gate got a task whose prompt was the word "yes" while the question kept ticking toward its timeout. The parse, the three-path lookup and the ack text now live in `confirmations.py` (`parse_answer` / `resolve` / `apply_answer` / `ambiguity_listing`) with the approve/decline verbs, so the Talk poller, the web POST and `!confirm` cannot drift.

**Falling through is required, not a fallback.** "yes" is an ordinary reply to a question the bot asked in prose, so `parse_answer` matching must not by itself suppress task creation — only `resolve` finding a parked question may, which is why `_chat_answer_confirmation` returns `None` rather than a string when nothing is pending. The match is **exact against fixed word lists** (surrounding whitespace stripped, case folded, and deliberately nothing more — collapsing *internal* whitespace would make `"do  it"` an answer, and every widening here widens the set of ordinary messages swallowed as an authorization decision) rather than a prefix test: a message that merely starts with "no" is a message, and swallowing it loses it. The intercept is also skipped for an **attachment-bearing** send — the file is the message whatever the caption says.

**The ordering is not cosmetic.** It sits after the `!command` block and *before* `_chat_create_web_task`, because an answer that reached that helper would cancel the question it is answering. Same reason the Talk poller orders its own check ahead of `ingest_message`.

**The exchange is written to `messages`, unlike every other inline result.** `confirmations.record_exchange` stores the answer as a `role='user'` row and the ack as `role='system'`, both with `task_id=NULL` — the `!steer` shape, since the `(room, role, task_id)` unique index reserves the per-task user slot for the original prompt and LLM-context reconstruction joins on `task_id`, so a NULL row is display-only and never re-paired as a phantom turn. A confirmation is an authorization decision and "did I approve that untrusted email?" deserves an answer after a refresh, which the `!command` inline-only precedent does not give. Existence-only like every other room write, so a synthetic email-thread token no-ops rather than minting a room. `!confirm` records through the same helper, and so does the Talk poller — which is what puts a Talk-given answer in the web view of that room. **The reverse does not hold**: a web answer writes `messages` rows and posts nothing to Talk, and unlike an ordinary web send it never reaches `_chat_create_web_task`, so neither `_mirror_web_turn_as_user` nor the `output_target="room"` mirror leg runs either. Answering in web leaves the Talk view showing the question alone. That asymmetry is inherited (Talk renders from Nextcloud, not from the canonical store) rather than introduced here, and closing it means giving the answer a real Talk post.

**Three things deliberately record nothing**, because none of them decides anything: a usage error, the ambiguity listing, and an answer given on a surface the transcript does not render. The ambiguity listing is the one worth naming — it is also the only branch that *consumes no question*, and the intercept returns before `_chat_create_web_task` where the rate limit lives, so recording it would let a client loop append transcript rows without bound. `_TRANSCRIPT_SURFACES` covers the third: `TRANSCRIPT_SURFACE_FILTER` renders a `role='user'` row only for `web`/`talk`/`email` while every `role='system'` row renders, so a `cli` or `repl` `!confirm` would leave a visible ack above an invisible question.

**The send response carries both `messages.id`s, and the client must stamp them.** `command_data` is `{kind: 'confirmation_answered', user_msg_id, system_msg_id}`; the store writes them onto the optimistic user row and the placeholder-turned-system row. `appendStreamedRow` drops a frame whose `msg_id` is already on screen, and that is the *only* guard available here — neither row carries a task id, so the `(role, task_id)` path cannot fire. Without the stamp the room stream's own echo appends a second copy of both halves. It also makes the two rows starrable and deletable without a reload. `cmd_confirm` returns the same payload on `CommandResult.data` for exactly this reason. The client deliberately refreshes nothing else on that kind: the question's inbox row is closed by `confirmations.apply_answer`, and its count belongs to the notification store — polled by the root layout on every route and carried here by the room stream's `notifications` frame. Reaching into that store from the chat session would make this the one route where the badge is maintained by hand.

**A retried answer replays; it must not re-resolve.** A send the server accepted but never got to report is re-POSTed with the same `client_msg_id`, and `_is_own_replay` cannot see this exchange — `db.find_send_by_client_msg_id` inner-joins `tasks`, and these rows carry no task id, so the row consumes the `(room_token, client_msg_id)` unique index while being invisible to the lookup that exists to resolve a retry. `db.find_confirmation_exchange` is the NULL-tolerant sibling, consulted before anything else in `_chat_answer_confirmation`, returning the stored ids and ack. Both failure modes it closes were found in review and one is an authorization defect: with no gate parked the retry fell through to `_chat_create_web_task` and took an `IntegrityError` on the index (a 500), and with a *second* gate parked in the meantime `resolve` found that one open and **approved a question the user never answered**.

**Path B is resolved to the canonical token before the lookup**, not only before the transcript write. A task parks under the canonical token, so on a promoted room an unresolved Talk token misses Path B and falls to Path C — which with a second question open answers neither and posts the listing instead.

**Path A works on web because the mirror below stamps the Talk id.** A web reply cites a canonical `messages.id`; `get_pending_confirmation_by_response_id` matches `tasks.talk_response_id`. The mirrored prompt row carries `external_ids={"talk": …}`, so `db.get_message_external_id` walks the citation back and an explicit reply to one of several open prompts picks that one instead of hitting the ambiguity listing. The citation is checked against **this room** first, so the endpoint does not become an id oracle for another's. No second id column was invented for it.

**A Talk-delivered notification is mirrored into that room's transcript** (ISSUE-242). `notifications._dispatch` treated `talk` and `web` as unrelated destinations: the `web` leg writes a `role='system'` row into `messages`, the `talk` leg posted to Nextcloud and wrote nothing — same token, same room, one surface got the message. Everything going through a *task* already crossed over (`scheduler._store_room_turn`, ISSUE-176's producer half); non-task posts — alerts, heartbeat notices, reminders, and the inbound-email confirmation prompt — never were. For the prompt that is silent mail loss, since the task auto-cancels at `confirmation_timeout_minutes`.

`_mirror_talk_to_room` writes a `role='system'` row after a successful Talk delivery. `role='system'` is what the `web` leg already writes, so it renders identically, rides the live room stream and counts toward unread — no new render path; `origin_surface='talk'` is provenance only, since `list_system_messages` filters on `role` alone. The gate is **room existence, not surface config** — the same rule `_store_room_turn` uses — and the token is resolved through `db.resolve_room_token` first so a promoted web room is not missed. `_dispatch` resolves a bare `talk` destination's token itself rather than leaving that to `_send_talk`, because the mirror needs the token the post actually landed on. Best-effort throughout: the Talk post has already happened, so a failed transcript row must not report the notification as undelivered. Not idempotent across a retried notification — nothing retries one today; if that changes, dedup on `external_ids.talk`.

**The double-write guard compares canonical rooms, not raw tokens.** A route naming both legs of one room must produce one row, and neither raw value is the room: a bare `web` leaf carries no channel and lands on `default_web_room_token`, while a promoted room's Talk token differs from its own. Both sides are resolved before comparing.

**The short lock wait on the mirror's connection is load-bearing.** This opens a *second* connection to a database a caller may already hold a write transaction on — the hazard the `web` leg has always had, and the reason `_deliver_dmarc_alerts`, `_deliver_confirmation_prompts` and `run_cleanup_checks`' buffered notices are structured the way they are. Making the `talk` leg a writer extends that hazard to **every** remaining `send_notification` call site, and those reached from inside a transaction are not all worth restructuring — the nightly sleep cycle holds one write transaction for a whole pass and notifies from deep inside it. At the default 30s wait such a caller stalls for 30s per notification, on the dispatch thread, where six of them trip `loop_stall_alert_seconds`. `_MIRROR_LOCK_WAIT_MS` (250ms) turns the worst case into a *dropped mirror* instead, which is the right trade: the notification itself has already reached Talk, and the confirmation prompt — the one case where the mirror matters — is delivered outside any transaction. `run_cleanup_checks`' ancient-pending notice was moved out of its transaction with this change, joining the expiry notice that was already buffered for the same reason.

Why the aux gap-fill could not have covered the confirmation case: a gated task's transcript mirror is withheld, so it has no `role='user'` row — and `_AUX_ROOM_SCOPE` reaches an email task only through that row. Widening it to admit gated rows would publish `tasks.prompt`, the attacker-supplied text the gate exists to hold back. The fix belongs on the delivery side, and it generalizes past confirmations.

The direct `client.send_message` calls in `transport/talk/inbound.py` bypass `_dispatch` and so are not covered by the mirror — but the confirmation acks among them are now recorded through `record_exchange` instead, which reaches the same transcript. The `!model` usage error at `:541` stays Talk-only on purpose: it is a reply to something the user typed *in Talk*, so the reader is by definition looking at Talk.

**A failed or cancelled turn is gap-filled from `tasks`, and bands by its message, not by its task row.** `messages` is the transcript spine, but a turn that never produced an assistant row has nothing there to render its error bubble from, so `_chat_room_messages` runs an auxiliary query over `tasks` scoped to failed/cancelled and merges it into the page. Banding that fill on `tasks.created_at` was wrong: `record_inbound` writes the task row and then the user message row, both defaulting to second-granularity `datetime('now')`, so a turn straddling a clock second is stamped up to a second before the spine row it belongs to. The page floor `t1` is the oldest spine row, so the excluded turn was exactly the page's oldest — and since a first load fetches `limit*2` spine rows, any room shorter than one page had its error bubble missing on **every** load, not intermittently. The aux-filled bubble also sorted above its own question, the transcript's final sort being on `created_at`. `_AUX_TURN_TS` coalesces the turn's user spine row `created_at` with the task's own stamp and is the banding, cursor and rendered key for aux rows; a spineless legacy turn falls back to the task stamp. Only the timestamp is coalesced, not the `id` tiebreaker, so a turn tying the page floor second but sorting below it by id can still split across two pages — the pre-existing limit of a timestamp-only band. The `COALESCE` is not sargable and gives up the range bound `idx_tasks_user_created` gave the raw column (0.003 ms → 3.3 ms per probe over 10k tasks, linear, twice per page load), so every bound carries a redundant sargable companion on the raw column (`_AUX_TS_ABOVE` / `_AUX_TS_BELOW`) with an hour of slack. The companion is only ever *looser* than the exact test it accompanies, which is what makes it safe; the slack absorbs a backwards clock step. `backfill_room_messages_from_talk_cache` is the one writer that stamps a user row far from its task, and it recovers completed turns only, so it can never meet a band scoped to failed/cancelled.

**Every room in the listing says whether it is on Talk, and the default room asks the registry.** Two halves of ISSUE-342. `_chat_list_rooms` emits `talk_token` — the room's `talk` binding ref, one membership-scoped `db.talk_refs_for_member` query for the whole payload — because a *promoted* room keeps `origin='web'` by design, so `origin` alone cannot answer the question `RoomSettings.svelte` asks (`origin === 'talk' || !!talk_token`). Omitting the key did not merely leave the badge stale: the 30s rooms poll merges `talk_token: fresh.talk_token` unconditionally, so each poll **erased** what the promote response had just written, and the room went back to offering "Also open in Talk" — which `_chat_promote_to_talk` then refuses, because a room with a binding is not promotable. The room PATCH carries `origin` and `talk_token` for the same reason: it is merged into the client's record, so a key the listing sends and the PATCH omits reads as absent to any consumer that replaces rather than spreads. The second half is `db.ensure_default_web_chat_room`, which `_chat_list_rooms` called *before* it read the registry: it counted `web_chat_rooms` handles, and a Talk room's handle is minted by that same listing a few lines later — so a user whose rooms all came from Talk looked room-less on their first web visit and got a web-origin `general` beside the Talk `general` provisioning had already made them. ISSUE-134 named this function in its by-token audit list and the pass was never taken. **The two callers want different things, and collapsing them is what made the fix dangerous.** The listing needs no room invented for it at all — it mints handles in its own loop — so it now calls the helper only when `list_member_rooms` is empty. The other caller, `transport.web.default_web_room_token`, resolves a bare `web` route: an alert, the execution log, a routed notification. Handing that the user's most recently active room was wrong twice over. A shared Talk room would deliver a personal alert in front of its other members — reproduced directly: register one room with two members, call the resolver, and the second member's feed carries the first's alert. And the provisioned set is `general`/`logs`/`alerts` with the entrypoint posting into `alerts` at boot, so activity order alone hands the default to whichever the daemon last wrote to — permanently, since the handle minted there becomes the user's oldest and the first branch returns it from then on. `_default_room_candidates` therefore excludes rooms with another member and rooms named by the user's `log_channel` / `alerts_channel`, and a user whose only rooms are shared or machine-owned gets a private `general`, which is the old behaviour and the right answer for delivery.

**A `talk` binding can go stale, and the promote button is what repairs it** (ISSUE-401). The ref was written once and never revisited: `db.add_room_binding` is `INSERT OR IGNORE` under `PRIMARY KEY (room_token, surface)`, the three inbound writers depend on that, and the only statement removing a `room_bindings` row is the room teardown. So a Talk conversation deleted in Nextcloud left a room holding a `surface_ref` naming nothing — `talk_channel_for_task`'s rung 1 returns it, the delivery plan takes the same route, and rung 1 deliberately ignores `rooms.archived` precisely because there is no rung below it that could rescue the case. Every Talk delivery for that room 404'd, permanently, with no way out short of deleting the room and its whole web transcript.

Three things were shut, not the two the report named. `_chat_promote_to_talk` refused on any existing binding; nothing could rewrite a ref; and `RoomSettings.svelte` hid the control entirely once `talk_token` was set, so a fixed endpoint would still have had no trigger. The fix is one path doing double duty: with a binding present the promote probes the bound conversation and replaces the ref only where Nextcloud says it is really gone.

**The bot's own 404 does not establish that, and reading it as though it did is the trap this feature is built around.** Talk's `GET /room/{token}` is participant-scoped, so it answers 404 both for a conversation that no longer exists and for one the bot has been removed from — a first-class state elsewhere in this codebase, which `transport/talk/inbound.py` handles where it un-hides a room the bot is "demonstrably back in". Both leave the binding unusable, which is what makes the wrong reading tempting; only one is unrecoverable. A removed bot is repaired by adding it back, whereas minting a replacement **forks a live conversation** — the original keeps its history and its other participants and is then reachable by nothing, since the binding no longer names it and the poller only sees rooms the bot is in. So `_talk_conversation_verdict` settles a 404 by asking again **as the requesting user**, who was made a participant when the room was promoted: still visible means `bot_removed` and nothing is touched, a 404 for them too means `gone`. Everything else — no user token configured, a 403, a 5xx, a timeout — is `unknown`, which refuses. A probe that failed says nothing about the conversation, and collapsing "could not tell" into "gone" would mint a Talk room on every transient blip.

The write is `db.replace_room_binding`, a **compare-and-set** rather than an `ON CONFLICT DO UPDATE` on `add_room_binding` — that would let a stale or misrouted inbound rewrite a good binding on any poll. It takes the ref the guard read (`None` for "there was none") and refuses when the row changed underneath, because the check and the write are separated by an OCS round trip that creates a conversation: two concurrent promotes interleave there, and the loser overwriting the winner would point the room at a conversation the winner is not using. The loser deletes the conversation it just made and hands back the winner's ref, so the orphan does not accumulate in Nextcloud and the losing client stops rendering the ref it read before the race.

**A successful replace invalidates two other pieces of state, both in the same transaction as the CAS.** `messages.external_ids` holds the room's Talk message ids, and those are per-conversation: after a rebind a stale one does not merely fail to resolve, it can name a *different* message in the replacement — and `db.get_message_external_id` feeds a web reply's Talk `replyTo`, so `db.clear_room_external_ids` drops them. And `talk_channel_for_task`'s **rung 0** returns `tasks.talk_delivery_token` absolutely, before the binding is consulted, so an in-flight task carrying the dead ref would go on delivering there whatever the binding now says; `db.clear_stale_talk_delivery_token` drops those tasks to rung 1, scoped to non-terminal rows in this room holding exactly the replaced ref. A finished task's column is a record of where its answer went and is left alone.

The endpoint answers `{status, room}` for the same reason the control had to come back — `live`, `bot_removed` and `unreachable` are neither errors nor successes, and rendering them as the old bare 404 is what made a dead binding look like a button that does nothing. `room_bindings` keeps no `updated_at`, so after a rebind the row reads as though it had always pointed here; the one breadcrumb is an info line naming the old ref, the new one and both cleanup counts.

What is deliberately not built is an explicit unbind. It would hand the same escape hatch to any other way a binding goes stale, but it also lets a user break a healthy room by hand, and nothing today produces a stale binding by a route the probe cannot see.

**Sidebar order is latest activity, newest first.** The sort key is `last_activity` — the `created_at` of the room's newest `messages` row, falling back to the room's own creation time so a room nobody has spoken in still has one and a freshly created room lands near the top rather than at the bottom. It is computed in `db.list_member_rooms` as `(SELECT created_at … ORDER BY id DESC LIMIT 1)` rather than a `MAX(created_at)`: the ids carry the same order and `idx_messages_room (room_token, id)` makes that one index seek per room instead of a scan over the room's whole history. `_chat_list_rooms` emits it through `_iso_utc`, the same normalization a message row's `created_at` gets, precisely so a streamed row's stamp can be written straight onto the room client-side. The frontend renders `$rooms` in store order, so the store's order *is* the screen's; `stores/roomOrder.ts` holds the two pure operations (`sortRoomsByActivity`, `touchRoomActivity`) and `applyRoomEvent` touches on every frame — the single funnel every message passes through, which is what keeps the order live for a Talk turn, a routed alert and the user's own send alike. Three constraints. The **stamp never moves backwards** (gap recovery and the reconnect replay both redeliver older rows, and a demotion there would drop the room the user just spoke in). The **30s rooms poll now re-sorts**, reversing its long-standing "no reorder" rule — that reconciliation is what recovers the order after a sleeping tab or a dropped stream, and it takes the newer of the two stamps so a response built before it was awaited can't undo a frame that landed in between. And the **`room` metadata frame carries no `last_activity`** for the same reason it carries no unread count — it is diffed per stream tick, so including a per-message field would turn every turn into a `room` frame; a room *appearing* in that frame is stamped client-side with now (its appearance is the activity), and the poll settles it. Two responses that omit the key are merged rather than adopted for the same reason: the room PATCH (a rename is not activity) and the create POST, which is why `_chat_create_room` stamps its own reply server-side.

**Live room-event stream** (`live-web-chat-room-stream` spec). The per-task SSE stream only ever covered a task the client itself started; everything else — a Talk-originated turn, a routed alert, an unread badge, a rename — rode `setInterval`. `GET /chat/stream` is a sibling of `chat_task_stream` that tails the canonical `messages` store instead of `task_events`, carrying **every room the user is a member of over one session-lived connection**. The seam between the two: the room stream is the "something happened" bus, the task stream stays the "here is the token-level detail" bus — a streamed `user` row whose task is still unsettled makes the client open a task stream for it, which is `pickUpNewInFlightTasks` made event-driven (and fixes the `pending_confirmation` skip, since the persisted `confirmation` event now replays). Cursor is `messages.id` alone — one monotonic integer over user turns, assistant turns and system rows — which is what closes the fast-turn hole _structurally_: a Talk turn that starts and finishes inside 200ms still writes two rows and both are tailed, so timing stops mattering. The producers are in a different process from the web server (separate systemd units / containers), so the web tier polls SQLite exactly as `events.py` prescribes; the change is _where_ the polling lives — server-side at ~1s as an indexed `id > :cursor` scan behind an O(1) `MAX(id)` gate, pushing deltas, instead of client-side at 5s refetching a 50-row page per open room. `db.list_room_events_since` shares SQL fragments with `db.list_messages_across_rooms` so the visibility predicate (membership minus dismissals minus archived) cannot fork, and rows are emitted in the **same shape the history endpoints emit** (`_cross_room_message_dict`) so `buildHistoryMessage` builds a streamed row and a reloaded row identically. Frame kinds: `message` (carries `id:`), `gap` (carries `id:`), `room` (metadata delta — rename / model / effort / added / removed; **no** `id:`), `message_deleted` (**no** `id:` — see below), and a `: ping` keepalive (**no** `id:`) — auxiliary frames must omit `id:` or EventSource's resume cursor lands in the wrong place. The **gap threshold** is split because neither side can see the other's variable: the server decides on _cost_ (`room_stream_max_batch` rows AND `room_stream_max_bytes` — a joined assistant row carries `execution_trace`, so row count alone measures the wrong thing), the client on _age_ (~60s of silence on reconnect or after a hidden tab, since a star toggled elsewhere or a Talk-synced read cursor is state the stream doesn't carry). Both converge on one recovery routine: reload rooms + the open room, then adopt the cursor — which is the server's max id **scanned**, not the last one sent, or the truncated rows are stranded. Frames landing during that reload are buffered and re-applied. The notif poller is gone; the rooms poll is demoted to a 30s metadata reconciler and **kept only because `GET /chat/rooms` drives the Talk→web read-state pull**. Aggregate views (All / Unread) and background-room previews are fed from the same frames. Knobs under `[web.chat] room_stream_*`; `GET /chat/events` is the polling-fallback snapshot; `_admin_chat_section` reports live connection count (the metric that would justify the deferred shared per-user broker).
